Force Name-Based, Then Re-Resolve

two loops — first forces everything to strings, second resolves for new source

Problem lib.equality is asymmetric

lib.equality/find-matching-column can match a name-based ref against ID-having columns (name → ID works). But it cannot match an ID-based ref against name-only columns (ID → name fails). This means we can't just call upgrade-ref naively — if Phase 1 produces ID-based refs, Phase 2 can't re-resolve them against the new source.

The asymmetry
;; This FAILS with lib.equality: ID-based ref → name-based columns ;; can't match [:field {} 42] against [{:name "ID"}] ;; no :id to match on ;; This WORKS fine with lib.equality: Name-based ref → ID-based columns ;; matches by name [:field {} "ID"] against [{:id 99, :name "ID"}] ;; finds it
The consequence: Phase 1 must produce name-based refs for all transitive dependents. If it leaves any refs as ID-based, Phase 2 won't be able to re-resolve them against the new source's columns. This means Phase 1 needs to force name-based output regardless of source type.

Design Two loops: force name-based, then re-resolve

Loop 1: Force all refs to be name-based (even for table → table swaps). This creates a universal intermediate format that lib.equality can always match from. Loop 2: Change the source, then call upgrade-ref normally. Since refs are now name-based, lib.equality can find matching columns and lib.ref/ref produces the correct format.

Why name-based is the universal pivot. Name-based refs are the only format that lib.equality can match against any column list (with or without IDs). By forcing everything to name-based in Loop 1, Loop 2 always has a matchable starting point. This also moves us toward a file-based system where field IDs don't exist.

Force Three options for forcing name-based output

The question: how do we make lib.ref/ref emit name-based refs even when the column has an :id? Three approaches, each with different trade-offs.

Set :lib/source

Set :lib/source to :source/card on the query context. This tells lib.ref/ref the source is a card, so it emits name-based refs.

Pro: Uses existing mechanism
Con: Lying about source type may have side effects

Strip :id from columns

Remove :id from column metadata before passing to upgrade-ref. Without an :id, lib.ref/ref naturally produces name-based refs.

Pro: Clean, no lying
Con: Mutating metadata feels wrong

New dynamic var

Add a var like lib.ref/*force-name-refs*. When bound to true, lib.ref/ref always emits names.

Pro: Explicit intent
Con: New API surface

Core upgrade-ref: Alexander's implementation

upgrade-ref
(defn- column-key [column] ((some-fn :lib/desired-column-alias :name) column)) (defn- upgrade-ref [query columns ref] (let [field-id (lib.ref/field-ref-id ref) field (when field-id (lib.metadata/field query field-id)) column (if field ;; ID path: resolve name, match by name (m/find-first #(= (column-key %) (column-key field)) columns) ;; Name path: lib.equality structural match (lib.equality/find-matching-column ref columns))] (if column (lib.ref/ref column) ref))) ;; Loop 1: lib.ref/ref forced to emit names ;; Loop 2: lib.ref/ref emits natural format
Same function, two behaviors. In Loop 1, lib.ref/ref is forced to emit name-based refs (via one of the three options above). In Loop 2, it runs normally and produces whatever the new source expects. The upgrade-ref function itself doesn't change — only the forcing context around it.

Strategy Why force name-based for all transitive deps

Making all transitive dependents name-based (even for card → table swaps) is intentionally permanent, not just an intermediate step. Name-based refs work with any source type and move the system toward a future where the app-db is replaced with a file-based system where field IDs don't exist.

Entity Type Loop 1 (Force Names) Loop 2 (Re-Resolve) Final Format
Direct dependent Force refs to name-based Change source + upgrade normally Correct for new source
Transitive dependent Force refs to name-based No source change needed Name-based (stays)
The bigger picture: Name-based refs are strictly more portable than ID-based refs. They work whether the source is a table, model, card, or eventually a file. Loop 1 upgrades the world; Loop 2 only needs to fix up the direct dependents whose source actually changed. Transitive deps just stay name-based — and that's a feature, not a compromise.
