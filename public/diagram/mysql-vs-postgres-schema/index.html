Concept Note · Workspaces v2

"Schema" means two different things in the same SQL word

The same noun behaves like a folder inside a database in Postgres, and like a synonym for "database" itself in MySQL. JDBC reflects that. Metabase's data model collapses it. Workspaces-v2 has to navigate all three at once.

01The two trees

The most direct way to see the difference is to draw the namespace tree each engine produces. In Postgres it has three levels — server, database, schema, table. In MySQL it has two — server, database, table — with the SQL keyword SCHEMA being a synonym for DATABASE, not an extra layer.

Postgres
three real levels — schemas live inside databases
postgres-server ├── database test_data │ ├── schema public │ │ ├── orders │ │ └── people │ └── schema canonical_xyz │ └── orders_summary └── database analytics └── schema public └── events one connection binds to one database; can see all schemas in it.
MySQL
two levels — "schema" and "database" are the same thing
mysql-server ├── database test-data (== schema) │ ├── orders │ └── people ├── database analytics (== schema) │ └── events └── database mb__isolation_X (workspace iso DB) └── orders_summary CREATE SCHEMA x === CREATE DATABASE x. No extra nesting. Privileges live at the database level.

02Where it shows up — column by column

The same word travels through three layers — the SQL grammar, the JDBC driver's metadata API, and Metabase's app-DB schema — and at each layer it lands somewhere different. Reading across a row tells you what to expect at every level for one engine; reading down a column tells you the whole pipeline for one concept.

Layer Postgres MySQL
SQL keyword SCHEMAWhat does CREATE SCHEMA x do? Creates a real schema (a namespace inside the current database). Distinct from CREATE DATABASE. Synonym for CREATE DATABASE x. "SCHEMA is a synonym for DATABASE" — MySQL Reference Manual.
Namespace nestingLevels above a table identifier Three: db.schema.table. The connection binds to one DB and can address all its schemas. Two: db.table. There is no extra layer between database and table.
JDBC TABLE_CATCatalog field on getTables() The database name (e.g. test_data). Mostly informational since one connection = one DB. The database name (e.g. test-data). This is the only namespace JDBC reports for MySQL.
JDBC TABLE_SCHEMSchema field on getTables() The Postgres schema (public, canonical_xyz, …). null. Always. MySQL has no schema-distinct-from-database, so this column has nothing to put.
Metabase :model/DatabaseThe app-DB row representing a connection One row per Postgres database the user added (e.g. test_data). :details.db = "test_data". One row per MySQL database the user added (e.g. test-data). :details.db = "test-data". Same 1-to-1 shape — it's just that the warehouse "schema" is a database.
Metabase :model/Table.schemaWhat sync writes for each Table row The Postgres schema name verbatim — "public", "canonical_xyz", etc. nil. Always. Sync just copies TABLE_SCHEM, which JDBC reports as null for MySQL.
qualified-name-componentsHow the QP qualifies identifiers [:schema] → emits "schema"."table" in compiled SQL. [] → emits a bare `table`. The connection's default DB resolves it.
Cross-namespace queriesCan a single statement reference two namespaces? Yes within one DB: SELECT * FROM s1.t JOIN s2.t. Across DBs: not without dblink/FDW. Yes across databases: SELECT * FROM db1.t JOIN db2.t works given GRANTs on both.
The translation

In Postgres, the SQL noun schema, the JDBC field TABLE_SCHEM, and the Metabase column :model/Table.schema all carry the same value — a real schema name. The vocabulary is consistent at every layer.

In MySQL, the SQL noun schema is a synonym for database; JDBC's TABLE_SCHEM is always null and the database name lives in TABLE_CAT instead; and Metabase's :model/Table.schema ends up nil for every MySQL Table. The same word means three different things — and the actual database-level identifier travels through a different field at each layer.

03Why workspaces-v2 cared

⚠The MySQL :db override bug

Workspace provisioning gives every workspace a private output namespace. On Postgres that's a new schema inside the same DB. On MySQL — because there's no schema layer — it has to be a brand new database (mb__isolation_44490_1933). Same workspace, two completely different physical shapes.

build-workspace-config merges :database_details over the canonical :details when wiring up the workspace user's connection. Postgres init-workspace-isolation! only puts {:user, :password} there — both safe to override. MySQL was ALSO putting :db isolation-db there, which clobbered the canonical :db. Result: the connection bound to the empty isolation DB. Sync enumerated zero tables. The whole workspace was invisible.

Before — the bug

init-workspace-isolation! :mysql returned a :database_details map that overwrote the connection's bound database, severing sync from the canonical input data.

{:schema           db-name
 :database_details
   {:user     user
    :password password
    :db       db-name}}
After — drop :db

The workspace user has GRANT SELECT on the canonical DB and ALL on the iso DB. The connection stays bound to the canonical DB; iso writes use fully-qualified db.table references the rewriter prepends.

{:schema           db-name
 :database_details
   {:user     user
    :password password}}

The fix mirrors the Postgres shape: :database_details only carries identity (user/password), never location (:db). On Postgres the location was never an issue because schemas live inside one DB. On MySQL the iso location is a different database, but the canonical-vs-iso routing belongs in the rewriter and on the WSD row's :output_schema — not in the connection details, where it would silently break sync.

04What this implies in practice

Three things to keep straight when reading workspaces-v2 code, especially anything that touches sync, remap, or the QP read path:

If you're looking at… …here's the MySQL gotcha
A :model/Table lookup with :schema On MySQL, every :model/Table.schema is nil. Code that does (t2/select-one :model/Table :schema "public" :name "x") works on Postgres but returns nothing on MySQL. Use a per-driver translation (see table-row-schema-value in the e2e test).
A workspace YAML {schema: prod_db} The wire format's :schema slot carries an AST position, not a vocabulary. On MySQL the value in that slot is a database name. The slot is named :schema because that's where the qualifier lands in the compiled SQL — not because MySQL has schemas.
A TableRemapping row :from_schema / :to_schema hold the warehouse-namespace name verbatim. On MySQL that's a database name. The QP rewriter uses these to prepend a qualifier to the bare `table` identifier MySQL emits, turning orders into `mb__isolation_X`.orders.
A "no isolation leak" assertion You can't filter (:schema row) to distinguish input-DB rows from iso-DB rows on MySQL — both are nil. Probe the warehouse via information_schema.tables instead, then assert no :model/Table row matches an iso-DB table name.
