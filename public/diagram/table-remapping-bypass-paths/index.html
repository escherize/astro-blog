Where can a query still miss the remap?

Workspace table remapping has two enforcement points in the QP. Anything that goes around the QP bypasses Phase 2 entirely. This is the inventory of every such path I could find.

branch · feature/workspaces-v2 method · grep + clj-surgeon outline scope · src + enterprise/backend

01How the remap engages

two enforcement points wired into the QP pipeline
QP entry
Query arrives
MBQL or native, from cards, dashboards, embeds, public links, transforms, sync, X-rays.
→
Phase 1 · preprocess
Mutate table metadata
Rewrites :metadata/table rows in the cached metadata provider so HoneySQL emits workspace identifiers. Skips native SQL — too early to parse.
→
Phase 2 · execute
Rewrite compiled SQL
SQLGlot pass over the final SQL string. Authoritative. Covers MBQL and native. Wired in execute.clj:51 only — anything that doesn't go through execute-middleware skips this.

 Both phases run. Cards, dashboards, public links, embeds. none covered

 All run through qp/process-query. Both phases apply. none covered
Sandboxing & connection impersonation
QP middleware
 Both run inside the QP pipeline. Phase 2 fires after sandbox transforms. Worth a targeted test that a sandboxed query against a remapped table emits workspace SQL with the sandbox filter intact. low partial
Action / writeback execution
writeback.clj:54 · actions/execution.clj:47
 execution-middleware here is [swap-destination-db, check-permissions] — no workspace SQL remapping. Phase 1 runs but doesn't touch native SQL, and actions are required to be native. Action SQL like INSERT INTO public.orders on a workspaced DB writes to canonical orders. Out of scope per current product policy. high · prod write leak
CSV upload — append / replace
upload/impl.clj:191 · update-csv!
 Uses driver/insert-into! / driver/truncate! directly. Destination built by table-identifier from a :model/Table row — never consults TableRemapping. User picks "orders" from the UI; remap says canonical → ws-orders; rows go into canonical. New-table uploads are safe (nothing to remap). high · prod write leak
Stale cache hits
middleware/cache.clj:79
 Cache key hashes the query, not the remapping store. A query cached pre-remap returns canonical results forever — never touches Phase 2. Small blast radius today (workspaces are provisioned before queries flow), but the failure mode is silent. Wire a cache invalidator off TableRemapping insert/delete. med · stale read leak
*skip-remapping?* dynamic var
remapping/core.clj:77
 Short-circuits both phases when bound true. Intended for display-only endpoints. No production binders today. Future footgun: if anyone ever binds it on an execution path, isolation evaporates silently. Either delete it or rename to make misuse obvious. latent watch
Model persistence DDL
postgres/ddl.clj · persist_refresh.clj
 Writes to a per-database persistence schema — doesn't intersect any remapped table. Reads (the model query) go through QP. If workspace isolation ever needs to apply per-workspace persistence caches, separate feature. none covered
Sync — describe-database · syncable-schemas
DB-level introspection
 Discovers tables (the entry point that creates remap candidates). Doesn't consult the remap by design. Correct — the remap maps known canonical tables to workspace copies; you can't remap something you haven't discovered yet. none covered
Connection / health checks
can-connect?
 Doesn't reference any table. Cannot leak. none covered

04What to do next

priority order — smallest change with highest impact first
1
Cache invalidation on TableRemapping change
Toucan2 after-insert / after-delete hook on :model/TableRemapping that invalidates cache entries for database_id. Five lines. Highest impact for the smallest change.
~5 LoC · 1 hook
2
Decide writeback policy
Either add apply-workspace-sql-remapping-middleware to writeback.clj's execution-middleware, or block actions on workspaced DBs at the API layer with a clear error. Both defensible — pick one and add a test.
~10 LoC · policy call
3
CSV upload remap resolution
In update-csv!, resolve the remap before computing table-identifier. Wrap with (or (ws.table-remapping/remap-table…) [schema name]) at every call site — or block uploads on workspaced DBs at the API layer.
~15 LoC · 4 call sites
4
Tighten *skip-remapping?*
No production binders today. Either delete the dynamic var, or rename to *skip-remapping-for-display?* and add a runtime assertion that it's never active during query execution. Make misuse loud.
~30 LoC · API rename
