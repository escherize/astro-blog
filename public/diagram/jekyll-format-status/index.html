The Two Problems

What's actually broken

Alexander identified two concrete problems. Everything else (nulls, derived fields, tag bloat) is secondary cleanup.

  • File/folder names are entity IDs - you can't understand your content by looking at the directory. Example: _HYuQcKFgF7dmwkiG9m3F_automatically_generated_dashboards/
  • Cross-file references are entity IDs - you can't find or understand what a reference points to without a second lookup. Example: card_id: HfDN2DwyzcpL1Js2LiVKQ

Both problems make git diff review and LLM authoring impractical. If you can't read the diff, the human-in-the-loop workflow is broken.

Alexander's Proposal

Format Option 1: entity IDs + name-path refs

  • File/folder names are human-readable (derived from entity names, deduplicated with _2 suffix)
  • Cross-file references use name-path vectors: [Our analytics, Success engineering, KPI question]
  • Each entity keeps an entity_id field inside the YAML for stable identity
  • File/folder names have no dependency on the real name - you can update name: in the YAML without changing anything else
  • Tags are just names: [hourly, daily] not the bloated serdes/meta structure
  • Null fields stripped

Open Questions

1. One format or two?

Is this replacing serdes for all use cases (multi-instance sync, backup/restore) or is it a separate format for the Jekyll/blueprint use case? Serdes needs upsert semantics. Blueprints load into fresh instances.

2. How do name-path refs interact with renames?

Ben raised this: if you rename a card, every file referencing it needs updating. Name-paths make this a grep-and-replace, but concurrent renames on branches create merge conflicts. Entity IDs avoid this entirely. The question: is grep-and-replace acceptable, or does this need tooling?

3. Load into instance vs serve off filesystem?

If the app DB is a rebuildable cache from files, the identity problem is different than if we're doing incremental upserts. Current notes say "app DB stays but is a cache rebuilt from files" and "no two-way file editing." Needs confirmation.

The Architecture Question

What determines the format requirements

The format debate can't be resolved without answering: what is the runtime model?

  • Files -> app DB -> serve (current direction): files are source of truth, app DB is runtime cache. Need stable identity for incremental sync. Entity IDs serve a purpose.
  • Files -> serve directly (aspirational?): no app DB for content. File path IS the identity. Entity IDs are inert.
  • Serdes replacement: if this format also powers multi-instance sync, entity IDs are load-bearing for upserts. Can't remove.

The current format proposal (entity IDs inside + name-paths for readability) works for all three. That's probably why it's converging there.
