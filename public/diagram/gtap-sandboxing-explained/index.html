GTAP Sandboxing & Source Replacement

group_table_access_policy — how sandboxing scopes data access

01 What is a Sandbox Policy?

A sandbox (formerly GTAP - Group Table Access Policy) restricts what rows a permissions group can see in a table. Instead of querying the real table, Metabase substitutes a scoping card (a saved question) that filters the data. The scoping card typically queries the same table it's sandboxing, with filters applied (e.g., WHERE region = {{user_attr}}).

sandboxes table schema
id INTEGER Primary key group_id INTEGER FK -> permissions_group - which group is sandboxed table_id INTEGER FK -> metabase_table - the table being sandboxed card_id INTEGER? FK -> report_card - the scoping question (nullable) attribute_remappings TEXT? JSON mapping user attributes to query params
Unique constraint: (table_id, group_id) - only one policy per group per table. When card_id is null, sandboxing uses column-based filtering via attribute_remappings instead.

02 How the Scoping Card Works

When a user in the sandboxed group queries the Orders table, the query processor middleware intercepts it and substitutes the scoping card's query. The card typically queries the same Orders table with a filter, so the user sees a filtered view of the real data.

03 The Source Replacement Problem

When you replace Orders with Orders_clone, source replacement updates all questions that reference Orders to point at Orders_clone instead. But the sandbox policy has two references that break:

Two things go wrong: The sandbox policy's table_id still points to the old Orders table (not updated by replacement). The scoping card now queries Orders_clone, but the policy doesn't protect that table. Result: the sandbox is effectively broken - it protects a table nobody queries anymore, and the new table has no sandboxing at all.

04 Scenarios

Current behavior (broken)

Replace Orders with Orders_clone

  • Replacement proceeds without warning
  • Scoping card updated to query Orders_clone
  • Sandbox table_id still points to Orders
  • Orders_clone has zero sandboxing
  • Users in sandboxed group see all rows
New behavior (our fix)

Block the replacement

  • Check sandboxes table for table_id = source
  • Found a policy - return affects-gtap-policies error
  • UI shows: "This table has sandboxing policies that block this replacement."
  • Admin must remove sandbox first, then replace, then re-add sandbox
No sandbox - no problem

Replace a regular table

  • No sandbox policies on the source table
  • GTAP check passes (no rows in sandboxes table)
  • Replacement proceeds normally
  • All other checks still apply (columns, FKs, etc.)
Card source - not affected

Replace a card/model source

  • GTAP check only applies to :table sources
  • Card replacements skip sandbox check entirely
  • Sandboxes are table-level, not card-level
