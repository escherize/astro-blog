Layer 1 - Data Capture (Runtime)
Ring Middleware Extracts Embedding Context
Every HTTP request passes through middleware that reads headers and the URI to determine what kind of client is making the request and through what route.
SDK Middleware analytics/sdk.clj
Reads headers and binds them to dynamic vars for the request duration:
  • x-metabase-client -> *client*
  • x-metabase-client-version -> *version*
  • URI prefix -> *route* (public, guest-embed, metabot, agent-api)
  • If client header contains -preview suffix, or route is /api/preview-embed/
  • PII headers (origin, referer, user-agent, IP) -> bound when analytics-pii-retention-enabled
Session Middleware session.clj
Resolves the current session and determines how the user authenticated:
  • Session -> LEFT JOIN auth_identity -> provider
  • Providers: password, jwt, saml, google, ldap, oidc, api-key
  • Bound as *auth-method* for the request

Layer 2 - Storage (App DB Tables)
Raw Data Written to App DB
Event handlers read the dynamic vars and persist the raw values. The data is non-lossy - original header values are stored as-is.
view_log table
Written when a user views a card, dashboard, collection, or table.
  • embedding_client - raw header value
  • embedding_route - derived from URI
  • embedding_version - raw header value
  • auth_method - from session provider
  • tenant_id - from current user
  • PII: hostname, path, user_agent, ip_address
query_execution table
Written when a query executes (card run, dashboard card, native query).
  • Same embedding columns as view_log
  • Plus: is_sandboxed, is_impersonated, is_db_routed
  • Plus: parameters (JSON-encoded)
  • Plus: running_time, result_rows, error, cache_hit
SQL views read from these tables
Layer 3 - SQL Views (Migrations)
Views Add Derived Columns at Query Time
Database views created by Liquibase migrations. They read from the raw tables and add computed columns like surface and is_preview. One SQL file per DB engine (H2, Postgres, MySQL).
-- resources/migrations/instance_analytics_views/view_log/v4/
CASE
  WHEN embedding_client = 'embedding-sdk-react' THEN 'sdk'
  WHEN embedding_client = 'embedding-iframe'   THEN 'iframe'
  WHEN embedding_client IS NULL               THEN 'internal'
  ...
END AS surface,
CASE WHEN embedding_client LIKE '%-preview' THEN TRUE ELSE FALSE END AS is_preview
v_view_log view
Exposes all view_log columns plus derived surface and is_preview.
v_query_log view
Exposes query_execution joined with query table, plus derived columns.
Per-engine SQL files: Each view has 3 files - h2-*.sql, postgres-*.sql, mysql-*.sql. MySQL uses TRUE/FALSE for proper BIT type inference. The CASE logic is identical across engines.

Layer 4 - Build-Time: YAML Authoring (Developer Workflow)
How the Serialized Content Gets Created
The YAML in resources/instance_analytics/ is authored by a developer on a Postgres app DB. It is not auto-generated - a human builds the models and dashboards in the Metabase UI, exports them, and checks them in. The field metadata (types, semantic types, FK relationships) is baked into the YAML at this point.
1 analytics-dev mode
Enable the analytics-dev-mode setting. This creates a non-audit copy of the Internal Metabase Database that you can freely edit. (The real audit DB is read-only.)
2 Build content in UI
Create models, questions, and dashboards using the Metabase question editor. Add custom columns, expressions, filters, FK mappings. This runs against a live Postgres app DB.
3 Serdes export
Export via serialization. This produces YAML files with database_type: bool, base_type: type/Boolean, etc. - reflecting what Postgres reports for each column.
4 Canonicalize + check in
Run yaml->canonical to normalize (replace user emails with internal@metabase.com, strip ephemeral fields). Commit to resources/instance_analytics/.
Implication: The YAML always reflects Postgres types. When loaded on MySQL or H2, the field metadata may not match what those engines would report for the same SQL view. For example, the YAML says database_type: bool for is_preview, but MySQL might report BIGINT for a CASE WHEN ... THEN TRUE column. We've observed MySQL showing 0/1 in the UI for columns the YAML declares as type/Boolean.

Layer 5 - Startup: Serdes Load (No Sync)
How Content Gets Loaded on Every Boot
The ensure-audit-db-installed! function runs at startup. It creates the audit Database record, then loads the YAML content via serialization. There is no periodic sync task for this database.
1 Install DB record
maybe-install-audit-db! creates a :model/Database with is_audit: true and id: audit-db-id (a fixed constant). Points at the app DB itself.
2 Adjust to source
adjust-audit-db-to-source! temporarily sets engine: "postgres" and lowercases all table/field names so the YAML entity IDs resolve correctly during import.
3 Serdes import
v2-load-internal! deserializes the YAML. Creates Table, Field, Card, Dashboard records directly - no sync runs. Field types come from the YAML, not from JDBC metadata.
4 Adjust to host
adjust-audit-db-to-host! fixes engine-specific differences: MySQL -> set schema to null; H2 -> uppercase table/field names; Postgres -> no-op (YAML was authored on Postgres).
5 Conditional sync
A schema sync runs only if the engine changed (i.e., YAML says postgres but host is MySQL/H2). This updates field metadata (e.g., timestamptz -> datetime) to match the actual host DB.
6 No scheduled sync
In sync_databases.clj, the sync-analyze task is explicitly skipped for the audit DB: "Not scheduling sync task for audit database". The audit DB is never synced on a schedule.
No sync means: The Field records (types, descriptions, FK targets) for the v_* view tables come entirely from the YAML, not from live JDBC introspection. When new columns are added to a SQL view, the corresponding field YAML must also be added and checked in, or the column won't appear in the Internal Metabase Database. The one exception: the conditional sync at step 5 runs :scan :schema which can discover new fields - but only on the first boot after an engine change.

Layer 6 - What Users See
Usage Analytics Collection
Admin > Usage Analytics. Pre-built dashboards showing content views, query performance, user activity. The models are Metabase questions that query the v_* views.
  • Most Viewed Content
  • Performance Overview
  • Person Overview
  • Content with Cobwebs
  • Dashboard / Question Overview
  • Subscriptions and Alerts
Custom Reports Collection
Users can create their own questions and dashboards querying the same underlying models. They can add custom columns, expressions, and filters without touching SQL views.
  • Filter by surface to see SDK vs iframe
  • Filter by auth_method for auth breakdown
  • Combine raw embedding_client + embedding_route
  • Group by tenant_id for multi-tenant analytics
  • Derive new columns with Metabase expressions
Key Architecture Insight
Non-Lossy Capture, Lossy-OK Derivation
Immutable Layer (Tables)
Raw values: embedding_client, embedding_route, auth_method. Stored exactly as received. Never transformed. This is the source of truth.
Mutable Layer (Views)
Derived values: surface, is_preview. Computed at query time. Can be changed by updating the view SQL in a new migration version.
Authored Layer (YAML)
Models and dashboards built by a developer on Postgres, exported via serdes, checked in. Field types baked from Postgres metadata. No live sync updates them.
Implication
Future decisions about how to categorize or filter embedding types can be made at the view or content layer without changing stored data. But new view columns need corresponding YAML field entries to appear in the UI.
