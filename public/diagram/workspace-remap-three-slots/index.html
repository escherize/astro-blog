Workspaces v2 · Internal explainer

Three slots cover every warehouse.

Workspace remap rewrites table identifiers inside compiled SQL. The remap row has three columns — db, schema, table_name — and they cover Postgres, Snowflake, BigQuery, MySQL, ClickHouse, SQL Server, and Redshift without a fourth dimension. Here's why.

§1The four-layer model

where each piece of warehouse identity actually lives

L4Conn
Account · Org · Region · Credentials
Snowflake account hostname, BigQuery service-account JSON, JDBC URL host. Lives in :model/Database.details. Picked up at connection time. Never appears in compiled SQL.
no slot · invisible to rewriter
L3AST
Database · Project
Snowflake DB name, SQL Server database, BigQuery project. The leftmost identifier in compiled SQL when the driver populates it (catalog.schema.table).
:db · Table.catalog
L2AST
Schema · Dataset
Postgres schema, BigQuery dataset, SQL Server schema. Also: ClickHouse database name — it sits at this AST position because that's where it appears in compiled SQL.
:schema · Table.db
L1AST
Table · Collection
The thing being addressed. Always populated. The slot every driver fills.
:table · Table.name
The rewriter operates on L1–L3 only. Layer 4 is invisible to it — by design. Anything you'd want to change at L4 is what DB Routing handles, by swapping the :model/Database row entirely. Different feature, different axis.

§3Why no Account / Org slot?

the FAQ that prompted this explainer

It's not in the SQL. Snowflake's account name lives in the JDBC URL host (xy12345.us-east-1.snowflakecomputing.com). BigQuery's project-as-credential lives in the service-account JSON. JDBC URL hosts live in :model/Database.details. The rewriter only sees the SQL string the QP is about to send. Anything outside that string can't be remapped.

Switching across L4 means switching connections. A different account, a different region, a different set of credentials — that's a different :model/Database row entirely. Workspace remap doesn't try to do this; it would be the wrong tool. DB Routing is the feature that swaps connections atomically without changing the SQL.

Workspace remap × DB routing on the same DB is fundamentally incompatible — each consumes the "database identity" degree of freedom for opposite purposes. We block the combination at the API layer (Tier A) and inside Phase 2 (Tier B). See 2026-04-30-workspace-remap-vs-db-routing.md.

§4Why three slots is enough — forever

a structural ceiling, not a current limit

SQL grammar caps at three identifiers.

Every SQL dialect we support emits at most catalog.db.name in front of a table reference. SQLGlot's AST has exactly three positions: Table.catalog, Table.db, Table.name. No vendor extends this — they can't, without breaking the parser ecosystem. So three slots is a structural ceiling, not just a practical one.

Cross-account access doesn't add a slot.

Snowflake "shares," BigQuery cross-project IAM, federated query tools — they all route through the connection or via a higher-level construct, never through a 4-part SQL identifier. So even the most exotic cross-warehouse workflows still come out the other end as 3-part SQL — which our three slots handle.

§5The empty-string sentinel rule

why "" beats NULL

  • Meaning. "" means this driver does not emit this AST level. Postgres has no catalog in its compiled SQL; MySQL has neither catalog nor db. The sentinel is honest about the absence.
  • Why not NULL? SQL unique constraints treat NULL as not equal to NULL. Two MySQL remaps would both insert successfully and silently collide later. The crash that surfaced the multi-cardinality work was literally NULL not allowed for column FROM_SCHEMA on MySQL.
  • Equivalence at match time. The Phase 2 SQLGlot rewriter and Phase 1's MBQL metadata override both treat "" as nil when matching incoming refs — so a schema-less MySQL query still hits the rewriter even though its AST has no schema position.
  • Driver dispatch. Which slots get "" vs. a real value is determined by driver/qualified-name-components. The same multimethod is authoritative for the writer (spec-for-table) and the rewriter (Phase 2).

§6One paragraph for Slack

drop this when somebody asks why there's no account slot

Workspace remap rewrites the strings that appear inside compiled SQL. SQL allows up to three identifier positions before a table name (catalog.db.name), so the remap row has three slots. Anything above that — account, region, credentials — lives in the connection, never in the SQL, and so isn't a remap concern. Switching across that layer means switching connections, which is a different feature (DB routing) entirely.
