Source Replacement API Flow

POST /api/ee/replacement/replace-source — enterprise feature

Overview

Source replacement lets you swap the data source of every card that depends on a given source. A "source" is either a [:card id] or [:table id] — anything that appears as :source-card or :source-table in a question's query. The swap is async: the API returns a run_id immediately and the actual work happens on a virtual thread, updating both MBQL and native SQL queries, field references, dashboard card viz settings, and parameter mappings.

Pre-flight Check

Before executing, the system validates the swap via check-replace-source. This runs automatically as a gate inside /replace-source too.

1
Reject same source
If old == new, returns :same-source error immediately.
2
Database match
Both sources must be in the same database. Cross-DB swaps return :database-mismatch.
3
Cycle detection
Checks whether the new source transitively depends on the old source. If so, the swap would create a circular dependency → :cycle-detected.
4
Column mapping
Compares columns by lib/desired-column-alias. For each old column, finds the matching new column. Reports: :missing-column, :column-type-mismatch, :missing-primary-key, :missing-foreign-key, :foreign-key-mismatch.
5
Return result
{ success: true/false, errors: [...], column_mappings: [...] }

Execution Engine

The runner operates in two sequential phases on a single virtual thread. There is no parallelism and no wrapping transaction — each card is updated individually. A failure mid-run leaves some cards swapped and others unchanged. Segments are also tracked in the dependency graph via segment-create/update/delete events.

  VIZ --> EVT["Publish card-dependency-backfill\n+ segment dependency events"]

Simplified field-ref handling. Both phases now use lib.equality/find-matching-column + lib.ref/ref for field ref resolution — name-based refs pass through unchanged. The MBQL swap is a single lib.walk/walk pass that handles both source-type swapping and field-ref remapping together via update-stage.
Native SQL rewriting. The system handles all 4 combinations: card→card (swap template tags {{#42-old}} → {{#99-new}}), table→table (AST-level SQL name replacement), table→card (replace FROM orders with FROM {{#123-slug}}), and card→table (inverse).
1000-Card Example

Suppose you have Card #42 ("Revenue Summary") and you want to replace it with Card #99 ("Revenue Summary v2"). Card #42 is used as a source by 1000 other cards, 800 of which reference it directly and 200 more that depend transitively (e.g., a card based on a card based on #42).

No wrapping transaction. Each of the 1000 cards is updated in its own transaction. If the run fails at card #600, the first 599 cards are already swapped — there is no rollback. The cancellation check only happens at progress-flush boundaries (every 50 items), so a cancel request may take up to 50 items to take effect.
Cluster-wide singleton. Only one replacement run can be active at a time, enforced by a UNIQUE constraint on is_active = true. Attempting a second concurrent replacement returns 409 Conflict. A Quartz job runs every 10 minutes to time out stale runs (>30 minutes).
