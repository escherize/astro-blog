Source Replacement

integration plan — new lib-be api → enterprise runner

Context

Source replacement lets users swap one data source (table or card) for another across all dependent queries, dashboards, and parameters. The operation runs in two phases: upgrade field refs to name-based, then swap the source and remap field IDs.


Alex P has built a new lib-be API with bulk metadata loading, smarter skip logic, and a single-pass field ID mapping. This page documents the integration plan for wiring it into the enterprise runner.

Step 1 — Upgrade Field Refs
1 Upgrade all field refs from ID-based to name-based across transitive dependents

Queries

  1. Find all transitive dependent queries (cards, transforms, segments, measures) via usages/transitive-usages
  2. Filter with should-upgrade-field-refs-in-query? — skip queries that are already name-based
  3. Collect entity IDs by calling lib/all-referenced-entity-ids on the filtered queries
  4. Bulk-load metadata with lib-be/bulk-load-query-metadata using the aggregated IDs
  5. For each query: call upgrade-field-refs-in-query, write to DB if changed
then dashboards

Dashboard Parameter Targets

  1. Find transitive dashboard dependents
  2. For each parameter mapping / click behavior target:
    • Call should-upgrade-field-ref-in-parameter-target? to filter
    • Collect entity IDs via lib/all-referenced-entity-ids
    • Bulk-load metadata via lib-be/bulk-load-query-metadata
    • Call upgrade-field-ref-in-parameter-target
  3. Write changed dashboards to DB
Step 2 — Swap Sources
2 Replace the source and remap field IDs across direct dependents
  1. Call build-swap-field-id-mapping ONCE — creates the source→target column mapping for all queries in a single pass
  2. For each direct dependent query: call swap-source-in-query with the field mapping. No metadata needed.
  3. For each dashboard parameter target: call swap-source-in-parameter-target with the same field mapping
Performance note: The swap phase does not need metadata loading. The field-id-mapping is computed once and reused across all queries. This is a significant improvement over the old code which recomputed mappings per-entity.
Implicit Joins Compatibility

The Problem

Implicit joins use [:field {:source-field 1} 2] — these are table-only. When swapping table→card, the field-id-mapping produces strings (column aliases), so :source-field can't be updated. The implicit join silently breaks.

Table → Table

Field-id-mapping produces pos-int? values. :source-field is correctly remapped. Works fine.

Table → Card

Field-id-mapping produces strings. :source-field is left unchanged. Implicit join breaks silently.

The Fix

  • In check-replace-source, check if any FK points TO the original table
  • If yes and target is a card, report :incompatible-implicit-joins error
  • FE: add to ReplaceSourceErrorType enum + getEntityErrorMessage
Decision: Schema-level check. Query metabase_field for any field where fk_target_field_id points to a field in the original table. If any exists and the target is a card → block with :incompatible-implicit-joins. Simpler and safer than scanning queries for :source-field usage.
Permissions

Backend

  • Hydrate :can_write in entity-value (dependencies/api.clj:276), inside :data for each node
  • Use mi/can-write? on the hydrated entity. All graph endpoints flow through entity-value via expanded-nodes
  • Runner skips non-writable entities silently
  • Load readable entities with SQL permission checks, hydrate :can_write, update only writable ones

Frontend (Alex P)

  • Use :can_write from graph endpoints to separate entities into editable vs view-only
  • Show view-only entities in a separate tab per Figma design
  • FE prevents user from including non-writable entities in the swap request
Dashboard Parameters in Step 2

Problematic Case

Card A has :source-table 1. A dashboard uses Card A with a filter referencing a field from table 1. When Card A is swapped to use :source-table 2, the dashboard parameter target must also be updated.


The dashboard is not a direct dependency of the changed source (table 1), but a direct dependency of a direct dependency (Card A).
