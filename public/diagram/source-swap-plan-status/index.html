2 — Use New API From Runner
Critical Path Partial
Rewrite the runner to use the new lib/lib-be API for both upgrade and swap phases. Upgrade preserves field-id based refs in the same stage as the data source. Swap remaps field IDs using column matching.
Upgrade + Swap example
;; before {:source-table 1} [:field {} 10] ;; stage 0 — field-id ref [:field {} "ID"] ;; stage 1 — name ref ;; after upgrade — doesn't change anything here ;; (field-id ref is in same stage as data source, so it's preserved) {:source-table 1} [:field {} 10] [:field {} "ID"] ;; after swap a) — source changes, field stays if columns match by name {:source-table 2} [:field {} 10] ;; kept — name matched in new source [:field {} "ID"] ;; after swap b) — source changes, field ID remapped {:source-table 2} [:field {} 20] ;; remapped — old field 10 → new field 20 [:field {} "ID"]
Field-ID swap rules
;; For every field-id-based ref with the original source: ;; 1. Find the old column ;; 2. Replace :source-table ;; 3. In the new list of columns, find the matching column ;; ;; Matching attributes: ;; - :name ;; - :join-alias ;; - :fk-field-id ;; - :fk-field-name ;; - :fk-field-join-alias ;; Plain ref [:field {} 1] ;; Ref with join-alias — matched separately [:field {:join-alias "A"} 1]

3 — Dashboard Parameter Targets
New Work Item Not Started
When swapping sources in direct table dependencies, we need to also update direct dashboard dependents of direct card dependents if the original source is a table.
Problematic case
;; Card A uses table 1 Card A {:source-table 1} ;; Dashboard has a filter referencing a field from table 1 Dashboard filter target: [:field {} 1] ;; After Card A is swapped to use table 2: Card A {:source-table 2} ;; The dashboard parameter target must also update: Dashboard filter target: [:field {} 1] → [:field {} 2]
Dependency chain
;; The dependency graph looks like: Table 1 (original source — being swapped) ↓ Card A (direct dep — source-table changes) ↓ Dashboard (direct dep of Card A, NOT of Table 1) ↓ Filter param target: [:field {} 1] → [:field {} 2] ;; Runner must traverse this extra hop: ;; for each direct card dep → find its dashboard deps → update params
The dashboard is not a direct dependency of the changed source (table 1). It's a direct dependency of a direct dependency (Card A). lib-be/swap-source-in-parameter-target handles the actual rewriting. The runner just needs to traverse this extra hop.
4 — Implicit Joins Check
Pre-flight Validation Not Started
Implicit joins ([:field {:source-field 1} 2]) only work with tables. When swapping table → card, if any table has an FK to the original table, implicit joins break.
;; Implicit join — :source-field references a FK column [:field {:source-field 1} 2] ;; After upgrade, field-id ref becomes name-based: [:field {:source-field 1} "X"] ;; Problem: :source-field is a FK, which only exists on tables. ;; If the original table is swapped to a card, this breaks. ;; Cards don't have FKs → implicit join can't resolve. ;; Table → table swap: OK (new table can have its own FKs) ;; Table → card swap: BLOCKED if any table has FK to original
BE changes
  • In check-replace-source: when table→card, check for FK refs to original table
  • Report :incompatible-implicit-joins in top-level :errors
  • Not needed for table→table swaps
FE changes
  • Add to ReplaceSourceErrorType enum
  • Add error message in getEntityErrorMessage
  • "The original table is referenced by a foreign key from another table and can only be replaced with a table and not a question or a model."
