Compilation Tracker Architecture

runner.clj → *compilation-tracker* → swap_verify.clj

The runner bulk-loads entities from the DB at each phase boundary and passes the exact loaded objects to the compilation tracker. The tracker never touches the database—it compiles from what the runner gives it.

1 — The Problem: TOCTOU
Time-of-Check to Time-of-Use (TOCTOU). When the tracker independently re-fetches from the DB, it may read a different state than the runner operated on. Between the runner's write and the tracker's read, the entity could have been modified again (e.g., by a concurrent request or the next batch). The compilation result wouldn't reflect what the runner actually saw.

3 — Three Phase Boundaries

The runner calls the tracker at three points during a swap. Each call follows the same pattern: bulk-load all entities, then pass the loaded map to the tracker.

:before-upgrade
Captures the baseline. Entities are in their original state before any field-ref upgrades. The tracker compiles everything and stores the snapshot. Later diffs compare against this baseline to attribute regressions.
:after-upgrade
Taken after field-refs/upgrade! has rewritten all entities. Regressions found here vs. baseline are attributed to the upgrade phase. These are field-ref normalization issues, not source swap issues.
:after-swap
Taken after source-swap/do-swap! has rewritten source references. Regressions found here vs. :after-upgrade are attributed to the swap phase—the actual source replacement.
;; Pattern at each phase boundary (runner.clj lines 100-104, 117-121, 141-145): (when *compilation-tracker* (lib-be/with-metadata-provider-cache (let [metadata-provider (lib-be/application-database-metadata-provider db-id) loaded (bulk-load-metadata-for-entities! metadata-provider all-transitive-dependents)] (*compilation-tracker* :phase-name {:entities loaded :db-id db-id}))))
4 — Complete Data Flow
        sequenceDiagram
          participant R as Runner
          participant DB as AppDB
          participant T as Tracker
          participant C as compile-loaded-entities
          participant S as snapshot-loaded-entities

          Note over R,S: NEW DESIGN — single source of truth

          R->>DB: bulk-load-metadata-for-entities!
          DB-->>R: loaded = {[:card 1] obj, [:transform 5] obj, ...}

          R->>T: :before-upgrade {:entities loaded, :db-id 1}
          T->>C: compile-loaded-entities(loaded)
          Note right of C: Iterates map directly
          C->>C: entity-compilable-query per entry
          C->>C: try-compile each query
          C-->>T: {[:card 1] {:compilable? true}, ...}
          T->>S: snapshot-loaded-entities(loaded)
          S-->>T: {[:card 1] dataset_query, [:transform 5] source, ...}
          T->>T: Store baseline snapshots

          Note over R: === upgrade! phase ===
          R->>DB: bulk-load + upgrade! per entity

          R->>DB: bulk-load-metadata-for-entities!
          DB-->>R: loaded (post-upgrade state)
          R->>T: :after-upgrade {:entities loaded, :db-id 1}
          T->>C: compile-loaded-entities(loaded)
          C-->>T: post-upgrade compilation results
          T->>T: find-regressions(baseline, post-upgrade)

          Note over R: === swap! phase ===
          R->>DB: bulk-load + do-swap! per entity

          R->>DB: bulk-load-metadata-for-entities!
          DB-->>R: loaded (post-swap state)
          R->>T: :after-swap {:entities loaded, :db-id 1}
          T->>C: compile-loaded-entities(loaded)
          C-->>T: post-swap compilation results
          T->>T: find-regressions(post-upgrade, post-swap)

New design: tracker receives pre-loaded objects at each boundary, never touches DB

Entity type coverage. The loaded map includes all entity types the runner handles: :card, :transform, :segment, :measure, :table, and :dashboard. The compilation functions extract the compilable query from each (:dataset_query for cards, :source :query for transforms, :definition for segments/measures) and skip non-compilable types.
5 — How You Know It's Correct
Guarantee 1
Same data, same moment
The runner calls bulk-load-metadata-for-entities! which does a single batched t2/select per entity type. The returned map is immediately passed to the tracker. The tracker's compile-loaded-entities iterates this map—it never calls t2/select.
  • Verify: grep swap_verify.clj for t2/select inside tracker path → zero hits
  • Verify: compile-loaded-entities takes a map, not entity tuples
Guarantee 2
No DB queries in tracker
The old compilable-query function made per-entity t2/select-one-fn calls. It's been replaced by entity-compilable-query which takes [entity object] and extracts the query from the object with a case expression.
  • Old: (t2/select-one-fn :dataset_query :model/Card :id entity-id)
  • New: (:dataset_query object) — pure map lookup
Guarantee 3
Consistent snapshots for diffing
snapshot-loaded-entities extracts the raw query/definition from the same loaded objects. So when find-regressions diffs before vs. after, both sides come from the runner's point-in-time view.
  • Old snapshot-all-entities used pmap + entity-query-snapshot → N DB reads
  • New snapshot-loaded-entities iterates the loaded map → 0 DB reads
Guarantee 4
Runner stays clean
No qp.compile or qp.preprocess imports in runner.clj. The runner only moves data loading to phase boundaries. All compilation logic stays in dev code (swap_verify.clj).
  • Runner passes data down; tracker doesn't fetch up
  • Clean dependency direction: dev → runner, never runner → dev
How to verify at the REPL. Run (sv/run-verified-swap! [:card X] [:card Y]) on a card with transforms, segments, or measures in its dependency graph. The phase attribution output should show non-zero compilation counts that include all entity types, not just cards. Compare the :entity-snapshots in the results atom—they should contain entries for [:transform ...], [:segment ...], and [:measure ...] alongside [:card ...].
