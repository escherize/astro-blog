Workspaces V2 / Internal Explainer

What we're building, and how it's used.

A safe way for an analyst with Claude to build a semantic layer against real production data — without their writes ever showing up in production, and without them having to think about that.

Heads up — this is a fast-moving project. The principles are stable; specific endpoints, file shapes, and emit details shift commit-to-commit. This page is a snapshot — verify against the branch before citing details.

An analyst should be able to build modeling against the real data — and write tables back to the warehouse — and have it feel like any other Metabase.
The goal in one sentence

The setup. Two instances. Two roles.

Workspaces V2 runs across two Metabase instances built from the same code. Which role each plays is decided at boot, by what configuration is present — not by which binary is running. Stats is the production-shared instance the company queries every day. Local is a copy on the analyst's laptop.

Parent · Stats
stats

Production-ish, multi-user. Owns the canonical schemas. Where workspace admins (data engineers) provision new workspaces and emit a config.yml that hands the workspace off to an analyst.

  • Role — admin / data engineer
  • State — Workspace + WorkspaceDatabase rows in app DB
  • Auth — sharing-key public reads
config.yml git pull
Child · Local
local

On the analyst's laptop. Single-user. Boots from a config.yml the parent emitted. The analyst (with Claude) builds transforms, dashboards, and cards here. Disposable — restart with a different file means a different workspace.

  • Role — analyst (with Claude)
  • State — full app DB (H2) plus an in-process atom for workspace config
  • Auth — superuser session for the bundled workspace user

Provisioning. A workspace is a name. Each database in it is a fresh isolation schema.

The workspace itself is just a name. Admin adds database/schema combinations to it, one at a time, and each add provisions warehouse-side resources synchronously. A workspace can hold one DB or several. Per-DB independent failure: if provisioning a database fails, the WorkspaceDatabase row stays in :unprovisioned state and the database isn't usable from the workspace.

  1. Create workspace A name. No databases yet. Initial state: unprovisioned.
  2. Add a database, with input schemas Pick a source database and which of its schemas the analyst can read. A WorkspaceDatabase row is inserted; provisioning runs synchronously next.
  3. The warehouse mints isolation The driver creates an isolation schema (mb__isolation_*) plus a workspace user with read access on the input schemas and write access on the new isolation schema. The output schema name is recorded on the WorkspaceDatabase row.
  4. Repeat for additional databases A workspace can hold multiple DBs. Each provisions its own isolation schema and user. Failures don't cascade — one DB succeeding and another failing is a normal mid-state.
  5. Open the door for handoff Admin enables sharing on the workspace by minting a sharing key (a UUID). Anyone with the key can fetch config.yml and DB metadata from the parent without authenticating.

The all-or-nothing emit. Today the parent's config.yml emitter throws 409 if any of the workspace's databases is non-provisioned. So in practice, "the file describes only successful DBs" is enforced at emit time, not by filtering.

Table remapping. Two illusions, kept consistent.

The point of table remapping isn't to surface a new concept to the analyst. It's the opposite: the analyst works in their normal way — pointing transforms at canonical names like public.orders_summary, building cards on top — and the remapping layer keeps that working without ever touching production's public.

To the analyst
Feels like a normal Metabase.

They author transforms whose target is a canonical name. They build cards and dashboards on top of those tables. They never type "isolation schema" or know one exists. The workspace is invisible.

To the warehouse
All writes are isolated.

Every transform write the analyst issues against public.orders_summary is rewritten before it reaches the warehouse — it lands in mb__isolation_x.orders_summary instead. Production's public is never touched.

The remapping layer is the bridge. It rewrites transform targets on the way out, and table references in queries on the way in — covering both MBQL queries and native SQL.

Writes — the transform path

When the analyst runs a transform whose target is (public, orders_summary) on a workspaced child, the dispatch wrapper calls resolve-transform-target before per-type execution. If db-workspace-schema returns a non-nil output schema for that database, the hook (a) records a TableRemapping row mapping canonical to isolated, then (b) returns the target with its :schema rewritten to the isolation schema. The transform's persisted definition still says canonical — only the in-flight execution is rewritten. That's what makes the merge-back property work.

Reads — the query path, in two phases

The QP middleware does the read-side rewrite in two phases because there's no single point in the pipeline where both structured query data and fully-resolved SQL exist together. Phase 1 runs in preprocessing: it walks the cached metadata provider, finds each :metadata/table whose (:schema, :name) matches a remapping, and mutates the table metadata in place. Downstream HoneySQL reads the rewritten values and emits workspace identifiers directly.

Phase 2 runs at execute time, on the fully-resolved SQL string — after snippets, card refs, parameters, and MBQL compilation have all run. It parses the SQL via SQLGlot (in GraalPy), walks the AST, rewrites every table reference to its workspace counterpart, and re-emits. This is the authoritative rewriter — it covers both MBQL-origin queries and native SQL queries the analyst wrote by hand. It fails closed: on parse failure, the query never reaches the warehouse. Better a loud error than a silent leak to production.

Status note. The rewrite is end-to-end-tested across drivers. As of 2026-04-29, MySQL and Snowflake have known remapping bugs being worked through; Postgres / Redshift / SQL Server / ClickHouse / H2 are passing. The cross-driver test harness now provisions a real second schema per driver (no longer a no-op).

The handoff. One file.

Stats hands a workspace off to local through a single file: config.yml. The file is consumed at boot by the existing Metabase config-file machinery (the same one that's been around since 0.45). After that initial read, there are no live calls between stats and local. A different file at boot means a different workspace; the only way to "switch workspaces" on local is to restart with a different config.

What the parent emits today

The config.yml the parent's emitter produces has three sections, each consumed by an existing section handler:

databases
One entry per workspace database, with the workspace user's credentials, host, and schema-filters-patterns set so local only syncs the input schemas (not the entire warehouse).
users
The workspace creator's real account (their email + name). This matters for merge-back: when the analyst's content gets exported back to stats via git, it's attributed to a real user, not a synthetic workspace@workspace.local.
workspace
The name plus per-DB input_schemas (read-only) and output_schema (write target). This is what populates the in-process atom on local at boot.

The config-file system also supports api-keys and settings sections, but the workspace emitter doesn't currently produce them — the developer-instance admin key is delivered separately via the MB_WORKSPACE_API_KEY env var, and remote-sync settings are configured by Claude during local setup.

About the default password. A few options were considered (env-var template, hardcoded value, pulling an access token). The team converged on a static default value — the local instance is throwaway, so something hardcoded like password is reasonable, with the expectation that an analyst who wants to harden it can change it after first boot. The earlier {{env MB_WORKSPACE_USER_PASSWORD}} template is being replaced with this.

State on local. App DB plus a small atom.

Local is still a regular Metabase instance. It has a normal app database (H2 by default) where it stores all the things Metabase normally stores: users, sessions, transforms, cards, dashboards, sync metadata, table rows. The atom is a small, separate piece of state that holds only the workspace's identity and per-DB input/output schemas — parsed once from config.yml at boot.

The split is intentional. Manager-side state on stats lives in :model/Workspace + :model/WorkspaceDatabase rows; local-side state lives only in this atom. They never share storage — by construction. On a single dev box that runs both roles, manager rows can't leak into the instance endpoints, because the endpoints don't read from those rows.

Auth. Asymmetric, by design.

Each surface picks the auth model that matches its threat surface. The two are intentionally distinct: parent's keys are never reused on the child, and vice versa.

Parent · Stats
Sharing key.

Admin enables sharing on a workspace by calling POST /workspace-manager/:id/sharing-key; stats mints a UUID. Anyone with the key can hit two unauthenticated read endpoints scoped by it:

/workspace-sharing/<key>/config/yaml

/workspace-sharing/<key>/metadata

No login. No header. Possessing the key is the auth. Admin rotates (POST again, new key replaces old) or removes (DELETE) to revoke.

Child · Local
Superuser session.

The config.yml the parent emits provisions a superuser at boot — the workspace creator's email plus a static default password (password) the analyst can change. Claude drives local through superuser-gated endpoints, including POST /api/ee/workspace-instance/sync to pull git changes after writing transform YAMLs.

A separate MB_WORKSPACE_API_KEY env var is the channel for a developer-instance admin key — explicitly distinct from the parent's sharing key.

Open: future evolution. A v2 might drop child-side auth entirely (single-user disposable instances arguably don't need it), or use the main instance to OAuth into the child instance. For now, superuser session on the bundled user is the simplest thing that works without a new auth class.

The Claude loop. From key to running build loop.

The analyst's experience is intentionally one-step: they run a Claude skill (metabase-workspace) with the sharing key, and a few minutes later they have a running local Metabase, the workspace's metadata loaded, git sync configured, and Claude ready to take build instructions.

  1. Fetch the workspace artifacts Claude downloads config.yml from the parent's /workspace-sharing/<key>/config/yaml URL and the metadata from /metadata. No authentication required — the key is the capability.
  2. Boot local Metabase Claude starts a Metabase instance with MB_CONFIG_FILE_PATH pointed at the downloaded file. The boot loader reads the three sections (databases, users, workspace) and populates the app DB and the atom.
  3. Configure remote-sync Claude wires up the git repo (remote-sync-url, branch, token) so the local instance can pull semantic-layer YAMLs from a repository the team controls.
  4. Initial git pull Local pulls existing transforms/cards/dashboards from the repo into its app DB. The analyst now has a populated workspace.
  5. The build loop begins Analyst tells Claude what to build. Claude writes transform YAMLs to the git repo, then calls POST /api/ee/workspace-instance/sync on local to pull and apply them. Local executes the new transforms — table remapping kicks in transparently — and the analyst sees results.
  6. Iterate, then commit Analyst reviews, asks for tweaks, commits the YAMLs to the repo. When happy, they merge to main.

The payoff. Canonical-named transforms survive the round-trip.

Throughout the build loop, the analyst writes public.orders_summary. Local rewrites the warehouse target to the isolation schema for execution — but the transform's persisted definition, in the app DB and in the YAMLs the analyst commits, still says public.orders_summary. Canonical names all the way down.

When the analyst merges to main and stats pulls those YAMLs, stats's transforms run against stats's public — its real production schema. The modeling layer activates. No rewriting, no schema-pinning, no human cleanup. The same transform definition that ran on the analyst's isolation schema runs on production, against the same canonical names, and produces the canonical tables it always promised to produce.

A workspace is a name plus some isolation schemas. The handoff is one file. The build loop is analyst + Claude + git. The merge is free.
