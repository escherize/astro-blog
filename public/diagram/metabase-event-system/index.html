Metabase Event System

publish-event! · methodical multimethods · derive hierarchy · fan-out dispatch

Metabase uses a publish/subscribe event system built on Clojure's derive hierarchy and Methodical multimethods. When something happens (card created, user logged in, setting changed), the system publishes a keyword event. Multiple independent handlers - audit logging, revision tracking, view counting, notifications - all fire in response via do-method-combination.

1 Core Architecture

The entire event system lives in four files. Everything else is handlers that plug into it.

Public API
metabase.events.core
Re-exports publish-event!, event-schema, Topic, and object->metadata from events.impl. This is the only namespace other code should require.
Engine
events.impl
Defines the publish-event! multimethod with do-method-combination (all matching methods fire). Includes the :around :default wrapper for validation and logging.
Validation
events.schema
44 Malli schemas registered per event topic. The :around method validates every event map against its schema before dispatch.
Init
events.init
Loads schemas at startup. Contains a warning: "DO NOT ADD MORE HANDLER NAMESPACES HERE." Handlers belong in their domain modules.
2 Event Lifecycle

Every event follows the same path: an API handler or model function publishes a topic + payload map, the :around :default method validates it, then every handler whose dispatch key matches via isa? executes.

Event lifecycle: publish -> validate -> fan-out to all matching handlers

Why fan-out matters. Standard Clojure multimethods pick the single most-specific method. Metabase uses Methodical's do-method-combination, which runs every method whose dispatch value matches via isa?. So when you publish :event/card-create, the audit log handler, the revision handler, AND the model persistence handler all execute independently. The original event map is returned for chaining.
3 Derive Hierarchy

Each handler namespace creates its own intermediate keyword (e.g. ::audit/card-event) derived from :metabase/event, then derives specific topics under it. This prevents handlers from stomping each other - two handlers can both subscribe to :event/card-create through different intermediate keywords.

Dotted lines = derive (child "is a" parent). One event fans out to multiple handlers via separate derive chains.

Anti-pattern: direct dispatch keys. If two handlers both wrote (defmethod publish-event! :event/card-create ...), the second would stomp the first. The intermediate keyword pattern avoids this - each handler owns its own namespace-qualified keyword.
;; How audit_log.clj subscribes to card events: (derive ::card-event :metabase/event) ;; "I am an event handler" (derive :event/card-create ::card-event) ;; card-create triggers me (derive :event/card-update ::card-event) ;; card-update triggers me (derive :event/card-delete ::card-event) ;; card-delete triggers me (methodical/defmethod events/publish-event! ::card-event [topic event] (audit-insert! topic event)) ;; log all three to audit table
4 Handler Registry

Every handler is a defmethod on publish-event! dispatching on a namespace-qualified keyword. Here are the major consumer systems:

Handler File Events Purpose Notes
Audit Log audit_app/events/audit_log.clj 30+ types Records all changes to the audit log table for compliance. Covers cards, dashboards, users, permissions, settings, databases, uploads, and more. Largest handler
Revisions revisions/events.clj card dashboard segment measure document transform Creates revision records via push-revision! for entity version history (undo, diff). Create + update only
View Log view_log/events/view_log.clj card-read dashboard-queried collection-read table-read Increments view counts and updates last_viewed_at timestamps. Inserts ViewLog records. Batched every 20s
Activity Feed activity_feed/events/recent_views.clj dashboard-read table-read card-query collection-touch Updates per-user recent views for the activity feed / home page.
Notifications notification/events/notification.clj user-invited comment-created slack-token-invalid transform-failed Triggers system notifications (email, Slack) for specific events.
Database Sync sync/events/sync_database.clj database-create Kicks off async metadata sync when a new database is added. Background thread
Driver Notify driver/events/driver_notifications.clj database-update database-delete Notifies drivers to close/refresh connection pools on DB config changes.
Last Login users/events/last_login.clj user-login Updates User.last_login timestamp.

Search Index search/appdb/core.clj setting-update Reindexes fulltext search when site locale changes. Async (future)
5 Concrete Example: Card Creation

When a user creates a question, this is the actual path through the system. The event is published after the database insert, and the original event map is returned so the API can continue processing.

  User->>API: Create question

  Around->>Rev: ::revisions/card-event handler
  Note over Rev: push-revision!
  Around->>Persist: ::persistence/event handler
  Note over Persist: Create PersistedInfo if model
  Around-->>Events: Return original event map

  Model-->>API: card

6 Key Patterns & Gotchas
:metabase/event is a type tag, not an organizer. It exists so the :around :default method can assert that every published topic is actually a registered event (via isa? topic :metabase/event). Without it, typos like :event/card-craete would silently no-op through the :default method.
Handlers must NOT use specific event keywords as dispatch values. If two handlers both write (defmethod publish-event! :event/card-create ...), the second stomps the first. Always create a namespace-qualified intermediate: (derive :event/card-create ::my-ns/event) then dispatch on ::my-ns/event.
New handlers go in domain modules, not metabase.events.*. The events/init.clj file explicitly forbids adding new handler namespaces under metabase.events.*. Instead, handlers live with their domain: metabase.audit_app.events, metabase.revisions.events, metabase.sync.events, etc.
Some handlers batch writes. View counts and last_viewed_at timestamps are NOT written synchronously. The view_log handler queues updates and flushes them every 20 seconds to avoid hammering the database on popular dashboards.
Event payloads are maps with :object and :user-id. Most events follow this shape: {:object <the-entity> :user-id <who-did-it>}. Some include :previous-object for diffs (updates), :details for metadata, or :object-id for lightweight reads.
