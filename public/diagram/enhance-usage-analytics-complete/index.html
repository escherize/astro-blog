Enhance Usage Analytics for Embedding

branch: enhance-usage-analytics-for-embedding — 10 tickets, 20 commits, all done

Embedding customers couldn't see how their embedded content was being used. The view_log and query_execution tables had basic embedding context (client, version) but lacked auth method, tenant, request metadata, and security enforcement flags. This branch adds all of that, creates analytics views to expose it, and gates PII behind a GDPR toggle.

GDPR / PII Gating
How PII extraction works
1. Check analytics-pii-retension-enabled setting at write time (not middleware time) - if false, return nil.
2. Get current Ring request via request.current/current-request - if nil (background jobs), return nil.
3. Extract embedding_hostname from Origin, embedding_path from Referer, sanitized_user_agent from User-Agent, ip_address from remote-addr / X-Forwarded-For.

Setting check at write time means toggling it takes effect on the very next write, no restart needed.
PII columns NOT exposed in
  • Audit views (v_view_log, v_query_log)
  • Activity feed API (only aggregates)
  • ViewLog (no direct API returning raw rows)
PII columns exposed in
  • Superuser-only /api/logs/query_execution/:yyyy-mm Acceptable: admin-only endpoint

Design Decisions & Rationale
auth_method bound in session middleware, not embedding middleware
The middleware stack runs bottom-to-top. embedding-mw runs before authentication is resolved, so it can't know the auth method. merge-current-user-info is where session vs API key is distinguished - we tag the request with :auth-method there, then bind-current-user binds *auth-method* alongside other per-request dynamic vars.
route-client-mapping instead of per-route +embedding-client wrappers
Original plan was +embedding-client wrappers around each route in api_routes/routes.clj. Instead, a centralized route-client-mapping table in embedding-mw keeps all surface derivation in one place. The derived-client function checks the URI against known prefixes and falls back to the header. Easier to maintain, test, and extend.
is_impersonated via rff wrapping (like is_sandboxed)
is_impersonated can't be set in query-execution-info because impersonation is determined during QP preprocessing, which runs after data capture. Solution: wrap rff in the EE impersonation middleware to set it on result metadata, then extract in the completing arity - same pattern as is_sandboxed. By contrast, is_db_routed IS available pre-pipeline (destination-database-id is already destructured), so it's just (boolean destination-database-id).
ip-address moved from request.util to request.current
Circular dep: sdk -> request.util -> analytics.core -> sdk. The analytics.core link exists because request.util uses prometheus counters for IP geocoding. request.current has zero analytics deps and is designed to grow. request.util/ip-address now delegates, preserving all callers.
Why dynamic vars for auth_method? (not just request map)
auth_method needs to be available at include-sdk-info time, which runs inside Toucan before-insert hooks. These hooks don't have access to the Ring request map - they only see the model map being inserted. Dynamic vars (*auth-method*, *client*) are the standard Metabase pattern for threading request-scoped context through to write paths that are decoupled from the request handler. Same reason *current-user-id* and *current-user* are dynamic vars.
