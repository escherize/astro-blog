01 / 14

the problem

Why Does Effect Exist?

JavaScript gives you try/catch and Promise for async + errors. They work, but they have blind spots:

1. Errors are invisible

When you call fetchUser(id), nothing in the type signature tells you it can throw NotFoundError or NetworkError. You just... hope you catch the right thing.

2. Dependencies are implicit

Your function secretly reaches into the environment for a database connection, an API key, a logger. Testing means mocking globals.

3. Composition is awkward

Chaining async operations with proper error handling leads to deeply nested try/catch blocks or .then().catch().then() chains.

EFFECT'S ANSWER

One type that tracks all three:

Effect<
  Success,  // what you get back
  Error,    // what can go wrong
  Requirements // what it needs to run
>

TypeScript catches the errors at compile time, not at 3am in production.

02 / 14

mental model

Effect = Lazy Promise
with superpowers

Key difference: A Promise runs the moment you create it. An Effect is just a description of work - nothing happens until you explicitly run it.

Promise (runs immediately)
// This fetch fires RIGHT NOW, even though
// nobody asked for the result yet
const p = fetch('/api/users');
// ^ HTTP request is already in flight!
Effect (waits for you)
// This just creates a description.
// No HTTP request happens yet.
const e = Effect.tryPromise(() =>
  fetch('/api/users')
);
// Nothing happened. It's a blueprint.

// NOW it runs:
Effect.runPromise(e);

why laziness matters

Because it's lazy, you can:

Compose first, run later

Build up a pipeline of 10 steps, add retry logic, add timeouts - then run the whole thing once.

Retry safely

Since it's just a blueprint, you can re-run the same Effect 3 times on failure. A Promise? Already done - no retries.

Test without executing

Swap in fake dependencies before running. No mocking libraries needed.

Backend example: Building an API endpoint that fetches from DB, validates, then sends an email. With Effect, you describe all 3 steps, add retry on the email step, and run the whole pipeline per request.

glossary

JS Terms
You'll See Here

Rejecting a Promise

When an async operation fails. Like fetch returning a network error. The .catch() handler runs, or the catch block in a try/await.

Resolving a Promise

When it succeeds. The .then() handler fires, or await gives you the value.

Throwing

When synchronous code hits throw new Error(...). Stops execution and jumps to the nearest catch. If there isn't one, your program crashes.

Generator function*

A function that can pause and resume using yield. Effect uses these so you can write yield* instead of await. Same idea, different mechanism.

quick refresher

Promises in 60 Seconds

// A Promise represents an async operation
// It either RESOLVES (success) or REJECTS (failure)

const promise = fetch('/api/users/42');

// Handle success and failure:
promise
  .then(response => response.json())  // resolved!
  .catch(err => console.error(err));  // rejected!

// Or with async/await (same thing, nicer syntax):
try {
  const response = await fetch('/api/users/42');
  const user = await response.json();
} catch (err) {
  // Could be NetworkError, TypeError, SyntaxError...
  // You have no idea. `err` is typed as `unknown`.
  console.error(err);
}

The problem: catch gives you unknown. You don't know what went wrong. Effect fixes this by tracking errors in the type signature.

creating effects

From JS Values to Effects

Function When to use Backend example
succeed(value) Wrap a known value. Like Promise.resolve() Return a default config
fail(error) Create a failed Effect. Like Promise.reject() Return a validation error
sync(() => A) Wrap sync code that never throws Read from an in-memory cache
try(() => A) Wrap sync code that might throw JSON.parse(body)
promise(() => P) Wrap a Promise that never rejects Trusted internal service call
tryPromise(() => P) Wrap a Promise that might reject fetch(), DB queries, etc.

Rule of thumb: Use try* variants when the code could fail. Use the non-try versions when you're 100% sure it won't. If you use sync/promise and it throws anyway, Effect treats it as a "defect" - an unexpected crash, like a panic.

in practice

express route handler
// Wrapping a DB call that might fail
const getUser = (id: string) =>
  Effect.tryPromise({
    try: () => db.users.findUnique({
      where: { id }
    }),
    catch: (err) => new DatabaseError({
      message: `Failed to fetch user`,
      cause: err
    })
  });

// Now the type tells the whole story:
// Effect<User, DatabaseError>
//
// Compare to the Promise version:
// Promise<User>  (errors? who knows!)
safe json parse
// JSON.parse throws on bad input
const parseBody = (raw: string) =>
  Effect.try({
    try: () => JSON.parse(raw),
    catch: () => new ParseError({
      message: "Invalid JSON body"
    })
  });

// Effect<unknown, ParseError>
05 / 14

running effects

Where the Rubber
Meets the Road

Effects are lazy blueprints. Running is when actual work happens. You should only run at the edges of your program - the entry point, the route handler, the script's main().

FunctionReturnsOn error
runSync The value directly Throws
runPromise Promise<A> Promise rejects
runSyncExit Exit<A, E> Returns failure (no throw)
runPromiseExit Promise<Exit<A, E>> Returns failure (no reject)

Exit? Think of it as a result wrapper: either Success(value) or Failure(cause). The *Exit runners give you the result without throwing, so you decide what to do with errors.

example: express app

// In your route handler (the "edge")
app.get('/users/:id', async (req, res) => {
  // Build the Effect pipeline
  const program = getUser(req.params.id).pipe(
    Effect.map(user => ({ status: 200, body: user })),
    Effect.catchTag("NotFound", () =>
      Effect.succeed({ status: 404, body: "Not found" })
    )
  );

  // Run at the edge - convert to Promise
  const result = await Effect.runPromise(program);
  res.status(result.status).json(result.body);
});
Your app ┌──────────────────────────────────┐ │ Effect world (compose, transform) │ │ │ │ getUser -> validate -> format │ │ (all lazy) │ └─────────────┬────────────────────┘ │ runPromise() ▼ ┌──────────────────────────────────┐ │ JS world (Express, actual I/O) │ └──────────────────────────────────┘

composing effects

Building Pipelines

These functions let you chain Effects together without running them. Think of it like building a recipe before you start cooking.

map(effect, fn) - Transform the result

Like Array.map() but for Effects. Takes the success value and transforms it. The function can't fail.

// Turn a User into just their name
getUser(id).pipe(
  Effect.map(user => user.name)
)
// Effect<string, DatabaseError>

flatMap(effect, fn) - Chain with another Effect

Your transform returns another Effect. This is how you chain async steps. Like .then() where the callback returns a new Promise.

// Get user, then get their orders
getUser(id).pipe(
  Effect.flatMap(user => getOrders(user.id))
)
// Effect<Order[], DatabaseError>

tap(effect, fn) - Side effect, keep original value

Do something (like logging) but the pipeline continues with the original value, not the result of your tap function.

// Log the user, but pass the user through
getUser(id).pipe(
  Effect.tap(user =>
    Effect.sync(() => console.log(`Found: ${user.name}`))
  ),
  Effect.flatMap(user => getOrders(user.id))
)
// Still passes the user to getOrders

promise equivalents

PromiseEffect
.then(x => y) -> map
.then(x => fetch(...)) -> flatMap
(no equivalent) -> tap
Promise.all() -> all

Why flatMap, not just map?

map wraps your return in an Effect. If your function already returns an Effect, you'd get Effect<Effect<...>> - nested. flatMap "flattens" that into a single Effect.

Same reason .then() auto-unwraps Promises - it's doing flatMap under the hood!

all - Run multiple at once

// Like Promise.all() - run in parallel
Effect.all([
  getUser(id),
  getOrders(id),
  getPrefs(id)
])
// Effect<[User, Order[], Prefs], ...>
07 / 14

syntax styles

pipe vs Effect.gen

Effect gives you two ways to write the same thing. Pick whichever clicks for you.

pipe style functional, point-free
// Data flows top to bottom through each step
const program = Effect.succeed(5).pipe(
  Effect.flatMap(x =>
    x === 0
      ? Effect.fail("division by zero")
      : Effect.succeed(10 / x)
  ),
  Effect.tap(result =>
    Effect.sync(() => console.log(result))
  )
);
generator style imperative, like async/await
// Reads like normal code. yield* = await
const program = Effect.gen(function* () {
  const x = yield* Effect.succeed(5);
  if (x === 0) {
    yield* Effect.fail("division by zero");
  }
  console.log(10 / x);
});

the mapping

async/awaitEffect.gen
async function -> Effect.gen(function*)
await promise -> yield* effect
return value -> return value
throw error -> yield* Effect.fail(e)

Generator style is usually easier if you're coming from async/await. It reads top-to-bottom like normal code, lets you use if/else and for loops, and avoids the nesting that pipe style can create.

Backend example: An order processing pipeline in generator style:

Effect.gen(function* () {
  const order = yield* getOrder(id);
  const stock = yield* checkInventory(order);
  if (!stock.available) {
    yield* Effect.fail(new OutOfStock());
  }
  yield* chargePayment(order);
  yield* sendConfirmationEmail(order);
  return order;
});

error handling

Errors as Data,
Not Surprises

Expected errors

Things you planned for. Tracked in the type system. Like a function saying "I might return NotFound or Unauthorized."

// Type: Effect<User, NotFound | DBError>
// The signature TELLS you what can go wrong
const getUser = (id: string) =>
  Effect.gen(function* () {
    const row = yield* queryDB(id);
    if (!row) {
      yield* Effect.fail(
        new NotFound({ id })
      );
    }
    return row;
  });
Unexpected errors (defects)

Bugs. Things that shouldn't happen. Like accessing null.foo. Not tracked in types - they represent programmer errors.

// These create defects (panics)
Effect.die("impossible state");
Effect.dieMessage("unreachable");

// Also: if you use sync() and it
// throws, that's a defect too.
Effect.sync(() => {
  throw new Error("oops");
  // ^ This is a DEFECT, not a
  //   tracked error. You promised
  //   sync() wouldn't throw!
});

Short-circuiting: Just like Promises, when an error happens the rest of the pipeline stops. The error bubbles up until something catches it. No more if (result.error) return; checks at every step.

catching errors

catchAll - Catch everything

getUser(id).pipe(
  Effect.catchAll(err =>
    Effect.succeed(defaultUser)
  )
)

catchTag - Catch specific error

// Only catch NotFound, let DBError
// propagate up to the caller
getUser(id).pipe(
  Effect.catchTag("NotFound", () =>
    Effect.succeed(guestUser)
  )
)

either - Move error to success channel

// Instead of failing, you get
// Either<User, Error> as the value
getUser(id).pipe(
  Effect.either,
  Effect.map(result => {
    if (Either.isLeft(result)) {
      // handle error
    } else {
      // use result.right
    }
  })
)

services

Dependency Injection,
Effect-Style

Instead of importing a database client directly (hard to test), you declare "I need a database" as a requirement in the type. Effect won't let you run the program until you provide it.

Step 1: Define what you need
// "I need something called UserRepo
//  that has a findById method"
class UserRepo extends Context.Tag("UserRepo")<
  UserRepo,
  {
    findById: (id: string) => Effect<User, NotFound>
  }
>() {}
Step 2: Use it in your code
const getUser = Effect.gen(function* () {
  const repo = yield* UserRepo;  // "give me the repo"
  return yield* repo.findById("42");
});
// Type: Effect<User, NotFound, UserRepo>
//                              ^^^^^^^^
//                     "requires UserRepo"
Step 3: Provide it when running
// Production: real database
getUser.pipe(
  Effect.provideService(UserRepo, {
    findById: (id) => queryPostgres(id)
  }),
  Effect.runPromise
);

why this rocks for backend

Testing is trivial

// Test: provide a fake
getUser.pipe(
  Effect.provideService(UserRepo, {
    findById: (id) =>
      Effect.succeed({ id, name: "Test" })
  }),
  Effect.runPromise
);

No mocking libraries. No monkey-patching. Just provide different implementations.

TypeScript enforces it: If your code needs UserRepo and you try to run it without providing one, TypeScript gives you a compile error. You literally cannot forget a dependency.

The Requirements channel ┌──────────────────────────────────┐ │ Effect<User, NotFound, UserRepo> │ │ │ │ provideService(UserRepo, impl) │ │ ▼ │ │ Effect<User, NotFound> │ │ Requirements satisfied! Can run. │ └──────────────────────────────────┘

the problem in JS

Resource Leaks

// Classic JS problem:
const conn = await db.connect();
const data = await conn.query("...");
conn.release(); // Did you remember?

// What if query() throws?
// conn.release() never runs!
// You just leaked a connection.
// The try/finally fix:
const conn = await db.connect();
try {
  const data = await conn.query("...");
  return data;
} finally {
  conn.release(); // Always runs
}
// Works, but manual and error-prone
// with multiple resources

scoped resources

Auto-Cleanup
with Scope

A Scope collects cleanup functions ("finalizers") and runs them when the scope closes - even if something throws. Think try/finally but composable and automatic.

// Define a resource with auto-cleanup
const dbConnection = Effect.acquireRelease(
  // acquire: open the connection
  Effect.tryPromise(() => db.connect()),
  // release: always close it
  (conn) => Effect.sync(() => conn.release())
);
// Type: Effect<Connection, Error, Scope>
//                                 ^^^^^
//             "has cleanup to run"

// Use the resource
const program = Effect.gen(function* () {
  const conn = yield* dbConnection;
  return yield* conn.query("SELECT * FROM users");
});

// Effect.scoped says "run cleanup HERE"
Effect.runPromise(
  Effect.scoped(program)
);
// Connection opens, query runs, connection
// closes - even if query fails!

Backend win: DB connections, file handles, temp files, HTTP connections - anything that needs cleanup. Define it once, never worry about leaks again. Effect composes multiple scoped resources naturally.

resilience

Retry & Repeat

Because Effect is lazy (a blueprint), you can re-run the same Effect on failure or success. A Schedule defines the pattern: how many times, how long to wait, whether to back off.

retry - On Failure

Try again when it fails. Great for flaky network calls.

// Retry 3 times with exponential backoff
callExternalAPI(data).pipe(
  Effect.retry(
    Schedule.exponential("100 millis").pipe(
      Schedule.compose(
        Schedule.recurs(3)
      )
    )
  )
)
// Waits: 100ms, 200ms, 400ms
// Then gives up

repeat - On Success

Run it again after it succeeds. Great for polling.

// Poll every 5 seconds, forever
checkJobStatus(jobId).pipe(
  Effect.repeat(
    Schedule.spaced("5 seconds")
  )
)

// Poll 10 times, 1 second apart
checkQueue().pipe(
  Effect.repeat(
    Schedule.spaced("1 second").pipe(
      Schedule.compose(
        Schedule.recurs(10)
      )
    )
  )
)

Schedule Combinators

Schedules compose. Mix and match strategies:

// Fixed interval
Schedule.spaced("1 second")

// Exponential backoff
Schedule.exponential("100 millis")

// Stop after N retries
Schedule.recurs(5)

// Combine: exponential but max 3
Schedule.exponential("100 millis")
  .pipe(
    Schedule.compose(
      Schedule.recurs(3)
    )
  )

Why this is hard without Effect: In plain JS, retrying a fetch() means wrapping it in a loop with sleep, handling backoff math, managing state. With Effect, it's one line: Effect.retry(schedule). Because Effects are lazy blueprints, retrying is just... running the blueprint again.

data types

Effect's Toolkit

Effect ships with data structures that are immutable, composable, and play nicely with the rest of the ecosystem.

TypeJS EquivalentWhy use it
Option<T> T | null No more if (x !== null) everywhere. Forces you to handle the "nothing" case.
Either<A, E> { ok: A } | { err: E } A result type. Right = success, Left = error. Useful when you want errors as values, not exceptions.
Chunk<A> Array<A> Immutable, lazy array. Better for pipelines because operations don't create intermediate copies.
HashMap<K,V> Map<K,V> Immutable. Uses structural equality (two objects with same data are equal), not reference equality.
HashSet<A> Set<A> Immutable. Same structural equality benefit - new Foo(1) and new Foo(1) are the same entry.

structural equality

In JS, === compares by reference. Two objects with identical data are still "not equal":

// Plain JS
{ name: "alice" } === { name: "alice" }
// false! Different objects in memory.

// This bites you with Sets:
const s = new Set();
s.add({ id: 1 });
s.add({ id: 1 });
s.size; // 2 (not 1!)
// Effect's Hash + Equal traits
class UserId {
  constructor(public n: number) {}

  [Hash.symbol]() {
    return Hash.number(this.n);
  }
  [Equal.symbol](that: unknown) {
    return that instanceof UserId
      && that.n === this.n;
  }
}

Equal.equals(
  new UserId(1),
  new UserId(1)
); // true!

the ecosystem

Beyond Core Effect

Schema

Data validation + transformation. Like Zod, but integrated with Effect. Parse API request bodies, validate configs, transform data between shapes.

Config

Typed env variables. Config.string("DATABASE_URL") gives you an Effect that reads from the environment. Missing? You get a typed error at startup, not a crash at midnight.

Stream

Pull-based streams. Like an Effect that produces multiple values over time. Processing large files, WebSocket messages, database cursors.

Match

Pattern matching. Exhaustive, type-safe switch on steroids. Great for handling different error types or API response shapes.
