CHAPTER 01

Two instances. Two roles.

Same Metabase code on both. One is the production-shared instance. The other is the analyst's disposable copy. They do not share state.

topology

stats & local

Two Metabase instances running the same code. The role each plays is determined at boot, by what configuration is present — not by which binary is running.

parent · stats
stats

Production-ish, multi-user. Owns the canonical schemas the company queries every day. Where workspace admins (data engineers) provision new workspaces and emit a config.yml that hands the workspace off to an analyst.

  • Role — admin / data engineer
  • State — Workspace + WorkspaceDatabase rows in app DB
  • Auth — UUID-gated public reads
config.yml git pull
child · local
local

On the analyst's laptop. Single-user. Boots from a config.yml the parent emitted. The analyst (with Claude) builds transforms, dashboards, and cards here. Disposable — restart with a different file means a different workspace.

  • Role — analyst (with Claude)
  • State — full app DB (H2) plus an in-process atom for workspace config
  • Auth — admin API key bundled in config.yml

CHAPTER 02

Provisioning

A workspace is a name. Each database you add to it gets its own isolation schema and warehouse user, minted on demand. A workspace can hold one DB or several.

lifecycle

A workspace can hold many DBs. Each one is provisioned separately.

The workspace itself is just a name. You add database/schema combinations to it one at a time, and each add provisions warehouse-side resources synchronously. If a provision fails, the database is left in the unprovisioned state and isn't usable.

01
Create workspace
A name. No databases yet. State: unprovisioned.
02
Add a DB + input schemas
Pick the source database and which of its schemas the analyst can read. A WorkspaceDatabase row is inserted; if provisioning fails it stays in unprovisioned.
03
Warehouse mint
Driver creates an isolation schema (mb__isolation_*) plus a user with read on the input schemas and write on the isolation schema.
04
Repeat for more DBs
A workspace can hold multiple DBs. Each adds its own isolation schema + user. Independent failure per DB.
05
Hand off
Stats emits config.yml from the workspace. Today's emitter requires every DB to be :provisioned (else 409). Analyst takes the file to local.
03
CHAPTER 03

Table remapping

The analyst on local works in their normal way — pointing transforms at canonical names like public.orders_summary. Behind the scenes, every write is rewritten to land in the workspace's isolation schema, and every read is rewritten to find it there.

why this matters

Two illusions, kept consistent.

to the analyst

Feels like a normal Metabase.

They author transforms whose target is a canonical name. They build cards and dashboards on top of those tables. They never type "isolation schema" or know one exists. The workspace is invisible.

to the warehouse

All writes are isolated.

Every transform write the analyst's local issues against public.orders_summary is rewritten before it reaches the warehouse — it lands in mb__isolation_x.orders_summary instead. Production's public is never touched.

The remapping layer is the bridge. It rewrites transform targets on the way out, and table references in queries (MBQL and native SQL) on the way in.

CHAPTER 04

config.yml

The handoff between stats and local is a single file. Stats produces it. Local consumes it at boot. After that, no live calls between them.

contract / one file

What's in it.

Sections are consumed at boot by the existing Metabase config-file machinery (`metabase-enterprise.advanced-config.file`). The analyst restarts local with a different file when they want a different workspace — there is no "switch workspaces" UI.

  • databases — host, credentials, schema-filters (so local only syncs the input schemas)
  • users — workspace creator's real account, so merge-back attributes content correctly
  • workspace — name + per-DB input_schemas and output_schema

The config-file system also supports api-keys and settings sections (e.g. for an admin API key or remote-sync URL). Today the parent's emitter produces only the three sections above; api-keys and settings are emitted out-of-band or set via env.

config.yml — emitted by parent version: 1 config: databases: - name: testing engine: postgres details: user: mb__isolation_a34_117 password: [redacted] schema-filters-type: inclusion schema-filters-patterns: github_raw users: - first_name: Dan email: dan@metabase.com password: {{env MB_WORKSPACE_USER_PASSWORD}} is_superuser: true workspace: name: github databases: testing: input_schemas: [github_raw] output_schema: mb__isolation_a34_117
child-side state

App DB + a small atom for workspace config.

Local is still a regular Metabase instance. It has a normal app database (H2 by default) where it stores users, transforms, cards, dashboards, sync metadata — everything Metabase normally stores. The atom is a small, separate piece of state that holds only the workspace's identity and per-DB input/output schemas, parsed once from config.yml at boot.

app DB (normal)

Where Metabase always puts things.

  • Users, sessions, permissions
  • Transforms (canonical-named)
  • Cards, dashboards, collections
  • Sync metadata, table rows
  • TableRemapping rows (canonical → isolated)
in-process atom

workspace identity, in memory.

  • Workspace name
  • Per-DB input_schemas + output_schema keyed by database id
  • Populated at boot by the :workspace section loader
  • Cleared on restart — re-read each boot
  • Drives db-workspace-schema, the gate for write redirection
auth model

UUID for parent reads. API key on local.

Two surfaces, two threat models. Each picks the auth that fits.

parent · stats

Child uses a sharing key to read from parent.

Admin enables sharing on a workspace via POST /workspace-manager/:id/sharing-key — stats mints a UUID. The analyst (or Claude) hits unauthenticated URLs scoped by it:

  • /workspace-sharing/<key>/config/yaml
  • /workspace-sharing/<key>/metadata

No login. No header. Possessing the key is the auth. Admin rotates (POST again) or removes (DELETE) to revoke.

child · local

Local has its own admin credentials.

The config.yml the parent emits provisions an admin user (the workspace creator, password from {{env MB_WORKSPACE_USER_PASSWORD}}) at boot. Claude drives local via superuser-gated endpoints — for example POST /api/ee/workspace-instance/sync to pull git changes after writing YAMLs.

A separate MB_WORKSPACE_API_KEY env var is the channel for the developer-instance admin key — explicitly distinct from the parent's sharing key.

The payoff

Canonical-named transforms survive the round-trip.

The analyst writes public.orders_summary. Local rewrites the warehouse target to isolation, but the transform definition still says public.orders_summary. The serialized YAML in git still says public.orders_summary. Merge to main. Stats pulls. Stats's transforms run against stats's public. The modeling layer activates — with no rewriting, no schema-pinning, nothing for the human to fix up.

A workspace is a name plus some isolation schemas. The handoff is one file. The build loop is analyst + Claude + git. The merge is free.
