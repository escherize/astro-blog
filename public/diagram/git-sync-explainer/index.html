How does git-sync actually work?

A walkthrough of metabase-enterprise.remote-sync.* — pulling content from a git repo, pushing changes back, what gets synced, how authentication is wired, and the moving pieces (settings, scheduling, the Source protocol, locks, conflict detection) that hold it together.

01The Source protocol

Everything starts at source/protocol.clj. Two protocols define the contract; git.clj is the only implementation today, but the abstraction leaves room for others (S3, file URL, …).

Source

A handle on a remote repository.

  • (branches source) — list remote branches
  • (default-branch source) — query HEAD on the remote
  • (create-branch source name base) — branch + push
  • (snapshot source) — fetch and pin a commit SHA
SourceSnapshot

A pinned point-in-time view (a specific git SHA).

  • (list-files snapshot) — every path in the tree
  • (read-file snapshot path) — UTF-8 string or nil
  • (write-files! snapshot msg files) — commit + push
  • (version snapshot) — the pinned SHA
Snapshots are atomic. Once you have a snapshot, the SHA never changes — even if the remote moves. Reads are consistent across calls. Writes go against the live branch ref, but the snapshot's SHA stays as the parent for the new commit.

Stale-cache recovery

Force-push on the remote can leave a commit our local cache references but no longer fetches.

  • snapshot wraps snapshot* in try/catch
  • On "Missing commit": clear cached repo
  • Re-clone, retry once
  • Errors that aren't stale-cache propagate
Isolated config

On startup, init.clj swaps JGit's SystemReader for one that ignores ~/.gitconfig and /etc/gitconfig.

Stops Metabase from inheriting unrelated git config from the host.

03Pushing — the write flow

Writes don't use a working tree. JGit assembles a fresh tree object in-memory from the file specs you hand to write-files!, creates a commit, advances the local branch ref, and pushes. The bare repo never has a checkout.

Managed directories. The GitSource is constructed with a set of managed-dirs (top-level path segments). On write, files in managed dirs that aren't in the new write set are dropped — that's how stale renames/deletions clean up automatically. Files in any other top-level directory are preserved verbatim. The set comes from serialization/legal-top-level-paths — collections, databases, actions, snippets, transforms, ….
No working tree. Look at write-files!: there's no git checkout anywhere. The commit is built straight from blob inserts and a synthesized DirCache. Saves time and disk; means the bare repo is the only on-disk artifact.

04What gets synced

The git Source is content-agnostic — it just shuttles files. The actual content is Metabase's serialization v2 format (YAML files with stable entity IDs). Two layers live on top of the protocol:

source.clj

Adapter to serialization

store! takes a stream of serialized entities, turns each into a {path, content} file spec where content is YAML from serialization-deep-sort, and hands them off to write-files!.

WrappingSnapshot wraps any snapshot with regex path filters — used to scope reads/writes to the legal top-level dirs.

impl.clj

The orchestrator

import! & export! — top-level entry points called by the API and the scheduler. Handle conflict detection, version tracking, transform-detection auto-toggle, the RemoteSyncObject table, async tasks, and recovery.

Also where the has-remote-changes? cache lives — a 60-second TTL on git SHAs so the UI can poll cheaply.

Two-direction tracking. RemoteSyncObject rows mark "this local entity is mirrored in git." Their :status column flips to "dirty" via events when the entity changes locally. Export flips them back to "synced". The is-dirty endpoint queries the table — that's the FE's "you have unpushed changes" badge.

All of git-sync's behavior is gated on these settings. They can be set via the admin UI or via env vars (most have :can-read-from-env? true).

The "is sync enabled" rule. remote-sync-enabled is computed as (some? remote-sync-url). There's no explicit boolean. So setting the URL alone turns sync on; clearing it (or leaving it blank) turns it off. check-and-update-remote-settings! in settings.clj handles the obfuscated-token-on-update dance and runs check-git-settings! (a real connection) before persisting.

06Authentication

Auth is HTTPS + a personal access token, with provider-specific username conventions. There's a credentials-provider multimethod that dispatches on the URL host. SSH is not supported; check-git-settings! explicitly rejects anything that isn't http, https, or file://.

Default (GitHub, GitLab)
;; defmethod :default
(UsernamePasswordCredentialsProvider.
  "x-access-token"
  token)

GitHub convention: token-as-password with the literal username x-access-token. GitLab accepts any non-empty username, so this works there too.

bitbucket.org
;; defmethod :bitbucket.org
(when token
  (UsernamePasswordCredentialsProvider.
    "x-token-auth"
    token))

Bitbucket's app-password convention. nil if no token, since public Bitbucket repos work without auth.

Adding a provider

Add a (defmethod credentials-provider :host.example.com [_url token] ...). Dispatch is on the URL's host, lower-cased.

For self-hosted GitLab/Gitea/etc., the default impl already works.

07Scheduling, locks & tasks

Imports and exports are async. Each runs as a virtual thread under a diehard/with-timeout, after acquiring a cluster-wide lock so two Metabase nodes can't sync the same git repo simultaneously.

auto-import (read-only)

task/import.clj registers a Quartz job that fires every remote-sync-auto-import-rate minutes (default 5). It does the cheap has-remote-changes? SHA comparison first, only kicks off a real import if the SHA moved.

manual operations (any mode)

The HTTP endpoints (POST /import, POST /export) go through async-import! / async-export! in impl.clj. Same lock, same task model — they just don't depend on the scheduler.

08Conflict detection

Git-sync has its own conflict semantics on top of git's. Conflicts here aren't merge conflicts — they're "would this import discard local changes the user didn't intend to lose?"

  1. Dirty local changes (export-time). If the local RemoteSyncObject table has "dirty" rows and someone tries to import, async-import! throws unless force? is true. Same on export when the remote moved since the last sync.
  2. Library conflict (first-import). Local instance has its own Library collection that isn't yet remote-synced, but the import contains a Library. Refuses without force? on first import (subsequent imports treat the Library as already-managed).
  3. Feature-disabled conflicts. Import contains Transform entities but remote-sync-transforms is off. impl.clj auto-flips the setting on (and back off if the remote stops carrying transforms) — the conflict only fires for non-import flag-driven mismatches.
  4. Snippets without Library. Import contains NativeQuerySnippet entries but the local Library isn't remote-synced. Snippets need the Library marked first.
  5. Namespace-collection conflicts. Special-namespace collections (transforms, …) with entity_ids that conflict with what's locally present under a different namespace.
  6. Stale-cache "Missing commit". The remote was force-pushed and our cached repo references a now-orphaned SHA. Auto-recovers via clear-cached-repo! + retry.

09Startup behavior

init.clj runs as a def-startup-logic! hook. It's where the JGit isolated SystemReader swap happens, plus the boot-time reconciliation between settings and local state.

sync enabled
  • If :read-only & no branch set: throw
  • If :read-only & dirty local changes: throw unless MB_REMOTE_SYNC_ALLOW=overwrite-unpublished
  • If no remote-synced collection exists: kick off an initial async import
sync disabled
  • If a remote-synced collection still exists: clear its sync flag
  • Local data stays; just stops being managed by git-sync
Why the throw on dirty + read-only. Read-only mode means "the remote is the truth." If local changes exist that the remote doesn't reflect, a silent import would discard them. The startup contract is "fail loudly so the operator notices, give them the escape hatch via env var."

Things that surprised me
  • Bare clone, no working tree — writes go through JGit's ObjectInserter.
  • Cache key is SHA-1(url + ":" + token) — token rotation = fresh clone.
  • remote-sync-enabled isn't a setting; it's (some? url).
  • Author is hard-coded "Metabase Library <library@metabase.com>".
  • SystemReader swap on startup so JGit ignores host gitconfig.
  • managed-dirs determines what gets cleaned up on write — files outside are preserved.
  • Stale-cache recovery is automatic on "Missing commit".
