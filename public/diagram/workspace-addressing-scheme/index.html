WORKSPACE-V2 / TABLE ADDRESSING / CANONICAL SCHEME

How table addressing works in workspace remap

A canonical ::table-spec with three slots — :db, :schema, :table — that maps every supported driver onto SQLGlot's AST positions, regardless of whether the warehouse calls its top level a "schema," a "database," or a "project."

1 The invariant

Slot names are AST positions, not warehouse vocabulary

SQL identifier grammar caps at three parts: catalog.db.name. We name those positions :db, :schema, :table after the SQLGlot AST fields they map to — not after what the warehouse vendor calls them.

:db
SQLGlot Table.catalog
leftmost
:schema
SQLGlot Table.db
middle
:table
SQLGlot Table.name
always present
:db . :schema . :table

Empty string "" means "this driver does not emit this AST level." The empty-string sentinel — not NULL — lets storage enforce a real unique constraint on (database_id, db, schema, table_name).

2 Per-driver truth table

What each driver populates

driver/qualified-name-components is authoritative: it returns the AST positions the driver emits natively. spec-for-table populates exactly those slots and zeroes the rest.

Driver qualified-name-components :db slot :schema slot warehouse term
postgres [:schema] "" schema name "schema"
redshift [:schema] "" schema name "schema"
h2 [:schema] "" schema name (PUBLIC) "schema"
mysql [] "" "" (cardinality upgrade) "database" (warehouse)
clickhouse [:schema] "" database name (sic) "database" (warehouse)
snowflake [:db :schema] database name schema name "database.schema"
sqlserver [:db :schema] database name schema name "database.schema"
bigquery-cloud-sdk [:db :schema] project id dataset name "project.dataset"

The slot named :schema carries what ClickHouse and MySQL call a "database" because that's the AST position those drivers' compiled SQL lands in. :db is reserved for true 3-part identifiers like BigQuery's project.

3 The funnel

One producer, many consumers

All addressing flows through spec-for-table. Storage, the rewriter, and YAML config all speak the same {:db, :schema, :table} shape.

PRODUCER
spec-for-table
Reads :engine + qualified-name-components, emits canonical map.
STORAGE
TableRemapping rows
3 columns/side, all NOT NULL DEFAULT ''. Unique on (db_id, db, schema, name).
REWRITER
replace-names
Strips "" sentinels, hands wildcards to SQLGlot, re-emits SQL.
WIRE
config.yml
Same shape, slots a driver doesn't populate are missing (not "").
4 Worked examples

Source SQL → spec → rewritten SQL

Two contrasting cases: MySQL upgrades cardinality (source has no :schema, output adds one), Snowflake preserves it (3 slots in, 3 slots out).

MySQL — cardinality upgrade
SOURCE SQL
SELECT * FROM `orders`
↓ spec-for-table
SOURCE SPEC
{:db    ""
 :schema ""
 :table  "orders"}
↓ rewriter applies remap
OUTPUT SPEC
{:db    ""
 :schema "ws_alice"
 :table  "orders"}
↓ re-emit
OUTPUT SQL
SELECT * FROM `ws_alice`.`orders`
Snowflake — 3-part preserved
SOURCE SQL
SELECT * FROM
  "ANALYTICS"."PUBLIC"."ORDERS"
↓ spec-for-table
SOURCE SPEC
{:db    "ANALYTICS"
 :schema "PUBLIC"
 :table  "ORDERS"}
↓ rewriter applies remap
OUTPUT SPEC
{:db    "WS_DB"
 :schema "WS_ALICE"
 :table  "ORDERS"}
↓ re-emit
OUTPUT SQL
SELECT * FROM
  "WS_DB"."WS_ALICE"."ORDERS"
5 Invariants

Five rules that govern the whole scheme

INV-1
One address type, one funnel
spec-for-table is the only producer. All consumers accept the same shape.
INV-2
Slots = AST positions
:db ↔ catalog, :schema ↔ db, :table ↔ name. Not warehouse vocabulary.
INV-3
"" at storage, missing on wire
Sentinel is a SQL constraint concern, not a contract concern. Loader normalizes.
INV-4
No 4th slot
Account, region, credentials live in connection details. Crossing them = different Database row.
INV-5
qualified-name-components is law
"Does this driver populate :db?" is answered by the multimethod, not the spec map.
✓ FIXED — surfaced by the addressing-truth-table tests

The test caught a real INV-5 violation in production code

Snowflake and SQL Server both declare [:db :schema] in qualified-name-components, but db-position-value in table_remapping.clj only branched on :bigquery-cloud-sdk — so :db fell through to nil and normalized to "". The slot that should hold the warehouse database name stayed empty. The new truth-table tests turned this hidden gap into a loud failure on the all-drivers run, fixed by adding the (:snowflake :sqlserver) arm: (:db (:details database)). 32/32 assertions pass. Doc and code agree.
