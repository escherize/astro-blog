Batch Cache Architecture

with-cache = with-batch-cache + with-memoize-cache

Three composable caches serve three independent entry points into entity resolution. Each cache batch-loads related entities on miss, exploiting FK relationships in the data model for spatial preloading. The caches compose via function calls - field cache delegates to table cache, which delegates to DB cache.

Entry Points

Three dynamic vars, each rebound by with-batch-cache to use the batch caches instead of direct DB queries. The public API is unchanged.

Callers Into the Cache
*export-field-fk*
export-result-metadata :id
export-result-metadata :fk_target_field_id
export-mbql :source-field
*export-table-fk*
export-result-metadata :table_id
export-mbql :source_table
generate-path "Table"
*export-database-fk*
(serdes/fk :model/Database)
generate-path "Table"
delegate to inner functions with cache fns

Cache Composition

Each inner function accepts lookup fns. with-batch-cache injects the batch caches. Without it, the dynamic vars fall back to direct t2/select-one queries.

Field Cache
export-field-fk
field-fn(id) -> {:id :name :parent_id :table_id}
table-fn(table_id) -> via table cache
db-fn(db_id) -> via DB cache
field-name-chain(id, field-fn) -> walk parent_id in memory
batch-load-fields
1. load-field-hierarchy(id) - recursive CTE
2. Get table_id from loaded field
3. Find FK-connected table IDs via fk_target_field_id
4. Bulk SELECT fields WHERE table_id IN (...)
Stores: {id: {:id :name :parent_id :table_id}}
After 1st miss
field_42 (requested) field_41 (parent) + field_43 field_44 field_45 ... same table + FK tables
export-field-fk calls export-table-fk
Table Cache
export-table-fk
table-fn(id) -> {:id :db_id :name :schema}
db-fn(db_id) -> via DB cache
Returns [db-name schema table-name]
batch-load-tables
1. Load target table
2. Find FK targets: fields with fk_target_field_id != nil
3. Resolve their table_id values
4. Load FK-connected tables up to limit
Stores: {id: {:id :db_id :name :schema}}
After 1st miss
table_7 (requested) + table_8 (FK target) table_12 (FK target)
export-table-fk calls export-database-fk
Database Cache
export-database-fk
db-fn(id) -> {:id :name}
Returns db-name (string)
batch-load-databases
1. Load target database
2. Load all other databases up to limit
(Most instances have <10 databases)
Stores: {id: {:id :name}}
After 1st miss
db_1 (requested) + db_2 db_3 all databases

make-batch-cache Internals

Generic cache factory. Each of the 3 caches is an instance of this. *batch-cache-max-size* (default 50,000) limits memory and SQL fetch size. Matters more for fetch limiting than JVM memory - JSON-unfolded tables can have millions of fields.

Cache lifecycle
On miss
Call load-fn(id, max-batch)
Returns {id: entity, ...}
Merge ALL returned entries into cache
(Sibling preloading)
On hit
Return cached entity
O(1) atom deref + map lookup
No DB queries
Eviction
FIFO via PersistentQueue
Old entries dropped when exceeding max
New batch entries NEVER evicted
(Parent chains stay complete)
Eviction example
field_42 field_43 field_44 field_45 | field_200 (new batch) field_201 field_202 old entries dropped to make room
Why 3 caches, not 1 joined query? A joined field+table+db query would help the field path, but *export-table-fk* and *export-database-fk* are called independently from export-mbql and generate-path - they'd still need their own caches. The three-cache design serves all access patterns while keeping each cache simple and independently testable.
