ghy-3211-async — async dependency analysis — 3 critical findings

1
TOCTOU Race in mark-stale!
dependency_status.clj:20-42 — High

The function uses a select-then-insert pattern: it queries existing IDs, then inserts any that are missing. Between the SELECT and INSERT, another thread can insert the same ID, causing a unique constraint violation. This is a classic Time-of-Check-to-Time-of-Use (TOCTOU) bug.

The Vulnerable Code

;; dependency_status.clj:20-42 (defn mark-stale! [entity-type entity-ids] (doseq [batch (partition-all mark-stale-batch-size entity-ids)] (let [existing-ids (t2/select-fn-set :entity_id ;; Step 1: CHECK :model/DependencyStatus :entity_type entity-type :entity_id [:in batch])] (when (seq existing-ids) (t2/update! ...)) (let [new-ids (remove existing-ids batch)] (when (seq new-ids) (t2/insert! :model/DependencyStatus ;; Step 2: USE (mapv ... new-ids))))))) ;; Another thread ;; may have inserted ;; between steps!

How The Race Happens

Two concurrent event handlers fire for the same entity (e.g., a card is created and immediately updated). Both call mark-stale! with the same entity ID.

Thread A — SELECT existing IDs → id 5 not found in dependency_status
Thread B — SELECT existing IDs → id 5 not found (same snapshot, no lock)
Thread A — INSERT id 5 → success
Thread B — INSERT id 5 → UNIQUE CONSTRAINT VIOLATION

Why It Matters

The exception propagates to mark-stale-and-trigger! which catches it and logs an error. But the entity is not marked stale and the backfill job is not triggered. The dependency graph for that entity silently becomes stale until the next modification.

Recommended Fix

Use an upsert (INSERT ON CONFLICT) or catch the constraint violation. The upsert approach is cleanest:

;; Replace the select-then-insert with a single upsert per batch. ;; Toucan2 doesn't have native upsert, so use raw SQL: (defn mark-stale! [entity-type entity-ids] (doseq [batch (partition-all mark-stale-batch-size entity-ids)] (t2/query {:insert-into :dependency_status :values (mapv (fn [id] {:entity_type (name entity-type) :entity_id id :dependency_analysis_version 0 :stale true}) batch) :on-conflict [:entity_type :entity_id] :do-update-set {:stale true}}))) ;; Alternative: catch constraint violation and treat as no-op ;; (the row already exists with stale=true from the other thread)

Same TOCTOU Race in upsert-status!
dependency_status.clj:44-57 — High

Identical pattern — select-one to check if a row exists, then branch into UPDATE or INSERT. Two concurrent completions for the same entity would both take the INSERT path.

The Vulnerable Code

;; dependency_status.clj:44-57 (defn upsert-status! [entity-type entity-id] (let [update {:dependency_analysis_version current-version :stale false} existing-id (t2/select-one-fn :id ;; CHECK :model/DependencyStatus :entity_type entity-type :entity_id entity-id)] (if existing-id (t2/update! :model/DependencyStatus existing-id update) (t2/insert! :model/DependencyStatus ;; USE — race! (assoc update :entity_type entity-type :entity_id entity-id)))))

Why It's Less Likely (But Still a Bug)

The backfill job uses @DisallowConcurrentExecution, so two instances of the job won't run simultaneously. However, upsert-status! is a public function — it could be called from other code paths, and even within a single job run, concurrent event handlers calling mark-stale! can create the row that upsert-status! is about to insert.

Recommended Fix

Same approach — use INSERT ON CONFLICT DO UPDATE:

(defn upsert-status! [entity-type entity-id] (t2/query {:insert-into :dependency_status :values [{:entity_type (name entity-type) :entity_id entity-id :dependency_analysis_version current-version :stale false}] :on-conflict [:entity_type :entity_id] :do-update-set {:dependency_analysis_version current-version :stale false}}))

Missing Feature Gate on ::segment-delete
