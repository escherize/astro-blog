Algorithm The unified swap: upgrade → change source → upgrade

Alexander's design: upgrade-ref is a single function that normalizes any field ref to the correct format for the current source. Swap is three steps: (1) upgrade with old source, (2) change source-table/source-card, (3) upgrade with new source. The same function handles all four source type combinations.

Core upgrade-ref: the branching logic

Each field ref is either ID-based (has a numeric field-ref-id) or name-based (string). The resolution path differs, but both end at lib.ref/ref(column) which always produces the correct format for the current source.

          end

Alexander's sketch — upgrade-ref
(defn- column-key [column] ((some-fn :lib/desired-column-alias :name) column)) (defn- upgrade-ref [query columns ref] (let [field-id (lib.ref/field-ref-id ref) field (when field-id (lib.metadata/field query field-id)) column (if field (m/find-first #(= (column-key %) (column-key field)) columns) (lib.equality/find-matching-column ref columns))] (if column (lib.ref/ref column) ref)))

FK Joins Implicit join field refs and the swap boundary

Implicit joins add complexity. A field ref like [:field {:source-field fk-id} target-field-id] has two field IDs to update — and which one changes depends on which side of the join we're swapping.

Implicit join ref structure
;; source is orders, joined table is products [:field {:source-field <orders.product_id>} <products.category>] ;; Swap the PK table: products -> products_2 [:field {:source-field <orders.product_id>} <products_2.category>] ;; ^ no change ^ changed ;; Swap the FK table: orders -> orders_2 [:field {:source-field <orders_2.product_id>} <products.category>] ;; ^ changed ^ no change
Hard boundary: We cannot swap a PK table used for an implicit join to a card. Cards don't expose FK relationships, so there's no way to resolve :source-field. This case should throw. Marked as week 3+ work.
Detection logic for the impossible case
;; [:field {:source-field <field-id>} <products.category>] ;; Fetch the field by field-id ;; Find the fk-target-field-id field ;; If its table-id is the original source table, ;; and we want to swap it to a card -> impossible (now)

Execution Two-phase execution with transaction boundary

Upgrading is safe without a transaction (idempotent, doesn't change source references). Swapping needs a transaction because it changes source pointers. Each entity can be swapped independently, and the dependency table updates immediately — so we can batch (e.g. first 500), then re-query deps. 

        graph TD
          api["API: start swap"]
          deps["Query dependency graph"]

          subgraph upgrade ["Phase 1: Upgrade (no transaction)"]
            u1["For each dependent entity"]
            u2["upgrade-query with old source"]
            u3["Save upgraded query"]
          end

          subgraph swap ["Phase 2: Swap (with transaction)"]
            s1["For each dependent entity"]
            s2["Change source-table/card"]
            s3["upgrade-query with new source"]
            s4["Save swapped query"]
          end

          progress["Report progress via runs API"]

          api --> deps
          deps --> u1
          u1 --> u2
          u2 --> u3
          u3 --> s1
          s1 --> s2
          s2 --> s3
          s3 --> s4
          s4 --> progress
Scale concern: With the stats DB we could see ~5000 dependent entities, 10k columns × 10k questions with joins. If it takes >1 minute, the async API with progress tracking handles it. Batching by 500 entities with incremental dependency re-queries keeps memory bounded.
