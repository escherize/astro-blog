Workspaces reorg — diff review

Code reorganization to make workspace seams discoverable by grep and unify two divergent table-remapping read paths into one.

Status: scoped 2026-05-01 (Bryan/Dan/Ben), not yet executed Scope: ~2 new files, 4 modified, mechanical only Branch: feature/workspaces-v2 Plan: ~/.claude/plans/dan-sutton-8-15-am-vast-wave.md Linear: GHY-3494
01Executive summary

Right now, grep workspaces in src/ doesn't find sync — five enterprise hooks live inline in fetch_metadata.clj, named after their consumer. The plan rehouses them under metabase.workspaces.sync and merges two read paths (one via t2/select, one via a protocol) into one.

The intuition. Metabase's defenterprise macro creates dynamic OSS→EE dispatch, which is invisible to text search. When a feature's stubs are scattered through consumer namespaces (metabase.sync.*, metabase.query-processor.*) and named after those consumers, you can't grep your way to the feature's surface. You have to already know the seams exist. That's fine for one-off hooks, but workspaces has eight seams across sync, QP, and transforms — discovery by archaeology is what eng lead Dan Sutton is pushing back on.

The fix has two halves. First, move the five sync stubs out of fetch_metadata.clj into a feature-named OSS namespace, mirroring the QP precedent. Second, collapse the duplicate read path: today, sync reads remappings via direct t2/select calls in table_remapping.clj, while QP middleware reads through a RemappingStore protocol in remapping/core.clj. After the reorg, both go through the protocol — which means sync tests gain access to the same MapRemappingStore seam that lets QP tests skip app-DB setup entirely.

The aha. table_remapping.clj (361 lines) shrinks to a writer module. remapping/core.clj (101 lines) becomes the canonical reader. A new workspaces.sync ns holds the five sync hooks. Three EE files instead of two — but each one has a single clear responsibility, and grep workspaces src/ now lights up every consumer subsystem.

Hard signal that this is real: the module linter is currently failing on the branch with errors that workspaces "should not be used in the actions / model-persistence / upload modules" — it sees the defenterprise edges that grep can't. After the reorg, those should drop to zero. Mechanical refactor only — no behavior change.

08Code review · Good / Bad / Ugly / Questions

Good

Single read path through the protocol good

Today, filter-workspace-side-tables at table_remapping.clj:177 calls all-mappings-for-db which does its own t2/select; QP middleware at query_processor/middleware.clj:175,247 calls remappings-for-db via the protocol. After the reorg, both go through the protocol — sync tests get the MapRemappingStore seam for free, and there is exactly one place to add caching, telemetry, or memoization later.

refs: table_remapping.clj:162-191 · remapping/core.clj:84-101
Feature-named OSS namespace makes seams discoverable good

The QP precedent (middleware.enterprise) is subsystem-named because it mixes EE stubs from sandboxing, impersonation, downloads, audit-app, and workspaces. Sync's 5 stubs are 100% workspaces — naming the new file workspaces.sync rather than fetch-metadata.enterprise means grep workspaces src/ actually surfaces it. Different problems, different naming choices.

refs: fetch_metadata.clj:17-65 · plan §Q1
clj-surgeon-shaped reorg good

This is exactly the cut-and-move-with-deps work clj-surgeon was built for. The plan sequences moves (readers first → sync hooks second) so each :extract! is a clean leaf. Compiler catches stragglers; tests gate each step. Mechanical work goes to the tool; judgment stays with the engineer.

refs: plan §Execution mechanics, steps 1-6
Banning direct t2/insert in tests is a real fix, not stylistic good

Three test sites at core_test.clj:131, api/instance_test.clj:29, api/instance_test.clj:52 bypass normalize-level. The empty-string sentinel for missing identifier levels is exactly the place where Postgres' NULL != NULL behavior in unique indexes bites — tests that insert nil into from_db can construct rows the unique constraint and SQLGlot rewriter treat differently than production. Closing this footgun before BigQuery (4-level remapping) lands is timely.

refs: table_remapping.clj:60-79 (sentinel logic) · table_remapping.clj:281-315 (add-mapping!)

Bad

defenterprise pairing rewrite is manual and silent-fail bad

Each OSS stub embeds the EE impl namespace as the second arg to defenterprise. The reorg has to rewrite five of these from metabase-enterprise.workspaces.table-remapping → metabase-enterprise.workspaces.sync. clj-surgeon won't do this — it's a value inside a form, not a structural move. A typo or miss means the EE impl never loads and the OSS fallback runs in EE production, which looks like the feature is just off. There's no compile error and no runtime warning. Mitigation: the plan calls this out (§Verification step 5), but it should be a checklist item, not a footnote.

refs: fetch_metadata.clj:23, 33, 42, 52, 62 — the second-arg symbols to update

Ugly

Three EE files instead of two — naming surface is denser ugly

Post-reorg, contributors need to know that "the table remapping module" is actually three: table-remapping (writers), remapping/core (readers + protocol), and workspaces.sync (sync hooks). That's an entirely defensible split, but it asks more of the reader than today's "everything is in table-remapping." Fix: require a docstring at the top of each that points to its two siblings ("readers live in remapping/core; sync hooks live in workspaces.sync"). Without that cross-reference, the next contributor will rebuild the god namespace by accident.

refs: post-reorg table_remapping.clj · remapping/core.clj · workspaces/sync.clj
RemappingStore is a one-impl-plus-test-double protocol ugly

AppDBRemappingStore is the only production impl. MapRemappingStore exists for tests. A reader hitting this file may decide the abstraction is over-engineered and try to inline it; doing so deletes the *remapping-store* seam that 8+ test namespaces depend on. The plan (§Q4) calls for a docstring sentence: "the protocol exists so tests can swap in map-store; do not add new impls without discussion." That note should be enforced — not optional — since the protocol's value isn't visible from one impl alone.

refs: remapping/core.clj:17-58
remap-table is silently 3-arg only ugly

The current remap-table at table_remapping.clj:134-149 matches by (from-schema, from-table-name) only — from_db is ignored. That is correct for Postgres-family + ClickHouse but incorrect for BigQuery: two projects with same-named datasets will collide. The docstring acknowledges this. The reorg moves the function to remapping/core verbatim, which means the bug moves with it. The plan punts to "out of scope," which is fair, but landing the reorg without addressing it means the next module landing BigQuery support will hit a fork in the road that wasn't there before the move.

refs: table_remapping.clj:134-149 · plan §Out of scope

Today, only QP middleware honors *skip-remapping?* (binding it skips remap during display contexts like POST /api/dataset/native). Once sync also reads through the protocol, enabled-for-db? would return false in the same scoped contexts — including any case where someone binds *skip-remapping?* while a sync runs. 09Decision log
Keep the "lie" model — sync writes canonical Table rows backed by isolation metadata high confidence · rejected alt

Decision. Workspace child instances continue to store one :model/Table record per logical table — canonical schema name, isolation-schema metadata. Queries against the canonical name get rewritten via :model/TableRemapping at query time.

Alternative considered (Ben, 2026-05-01): sync everything in the data warehouse honestly, expose isolation tables as their own Table records, filter them out on the read side (UI lists, search, query builder, joins).

Why the alternative was withdrawn. Dan's pushback: "lots of stuff expects: if it's in the database, I can use it." Search would surface isolation tables. Query builder would offer them as joins. Model index would index them. Result: whack-a-mole filters across every consumer of the Table model. Storing rows you always filter is also wasteful (Ben acknowledged — real but minor). Ben withdrew once Bryan clarified that the current model stores one record (canonical name, isolation metadata), not two. Quote: "that decision alleviates a lot of the need to fix up the view of the world on the read side."

What this means for the reorg. Don't propose surfacing isolation-schema tables in the UI. The reorg is mechanical — co-locate the existing seams, don't redesign them.

Source. Meeting transcript, 2026-05-01 9:30 AM (Bryan/Dan/Ben).

Decision. Create metabase.workspaces.sync rather than metabase.sync.fetch-metadata.enterprise.

Rationale. Dan's stated goal is grep discoverability of workspace seams. The QP precedent at middleware/enterprise.clj is subsystem-named because it mixes hooks from many features. Sync's five stubs are 100% workspaces — no mixed tenancy.

Three EE files; option (c) over collapse or partial unify high confidence

Decision. Keep remapping/core separate from table_remapping; spin off sync hooks to a new workspaces.sync.

Rationale. Collapsing (option b) deletes the *remapping-store* test seam relied on by 8+ test namespaces. Partial unify (option a) leaves sync still reading directly. Option (c) gives one read API for everyone, gives sync its own greppable home, shrinks table_remapping to a coherent writer module.

Alternatives. Collapse all into one ns; or keep both EE files and partially unify reads.

Decision. *skip-remapping?* and *remapping-store* stay in remapping/core.

Rationale. Moving them near QP would re-couple the abstraction to one consumer at the moment sync starts using it too. The dynamic vars are intrinsic to the protocol's contract.

Rationale. If sync hooks are extracted first, clj-surgeon's :extract! will pull all-mappings-for-db along into workspaces.sync (because it's an exclusive private dep). We want it in remapping/core. defenterprise refactor is tech-radar — explicitly out of scope high confidence · scope guard

Decision. The reorg keeps defenterprise as-is. Ben's deeper concern — that defenterprise decouples namespace-loading edges from call-site edges — gets a tech-radar entry, not a code change.

Rationale. Ben's idiomatic alternative is to construct a single protocol-instance object early in boot (with EE or OSS impls per method depending on jar contents), pass it to consumers. 10Re-entry context
Note from present-you to future-you

Key invariants

  • Sync hooks are :feature :none — they engage on row existence in table_remapping, not on premium token state. Rationale: workspace children boot before token install. The reorg must preserve this; do not accidentally add a feature gate when moving impls.
  • Empty-string "" is the sentinel for "this driver doesn't emit this identifier level," not nil. Rationale: Postgres/MySQL/H2 treat NULL != NULL in unique indexes. normalize-level in table_remapping.clj:67-70 is the only enforcer — keep it on every write path.
  • Phase 2 SQL rewriter fails closed: parse failure throws, no fallback to original SQL. Don't "fix" this during the move; silent pass-through breaches workspace isolation.

Non-obvious coupling

  • after-insert and before-delete hooks on :model/TableRemapping invalidate the QP results cache. Tests that bypass add-mapping! with direct t2/insert! still trigger this — but tests that delete via raw SQL won't. Stay on the typed model.
  • workspace-mode? (instance-level) and db-workspace-schema (per-database) and enabled-for-db? (per-database, by row existence) are three different gates. core.clj:6-19 documents this. The reorg doesn't touch these but moves around the third one — keep that doc-block aligned post-move.
  • Sync hooks call each other implicitly via the diff/inject pair: filter-workspace-side-tables drops to-side tuples, inject-workspace-canonical-tuples adds canonical tuples — together they make the sync diff stable. They must continue to share a read source (one all-mappings-for-db call per sync, not five) post-reorg, or sync gets noisier.

Gotchas

  • Five second-arg defenterprise symbols (fetch_metadata.clj:23, 33, 42, 52, 62) need rewriting from metabase-enterprise.workspaces.table-remapping to metabase-enterprise.workspaces.sync. Not structural — manual Edit. A miss is silent: the OSS fallback runs in EE.
  • remap-table is 3-arg — schema + table only — and ignores from_db. Correct for Postgres/ClickHouse, broken for BigQuery. Out of scope for this reorg, but keep the docstring intact when moving.
  • MapRemappingStore auto-widens 2-tuple keys to 3-tuples with empty db sentinel for back-compat (remapping/core.clj:55-57). If sync tests start using it, they may pass 2-tuples too — make sure the widening is visible in the docstring after the move.

Don't forget
