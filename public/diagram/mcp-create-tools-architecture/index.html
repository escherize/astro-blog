2 - Two Tool Systems (The Surprise)
The discovery that shaped the design. Metabase has two separate tool systems - and only one of them is exposed via MCP. The internal "Metabot" tools (charts, dashboards, alerts) use a completely different registration pattern and are invisible to external MCP clients. Knowing which system to extend was the critical first question.
INTERNAL Metabot Tools
Used by Metabase's built-in AI assistant. Defined with mu/defn metadata or deftool macro in metabot/tools/. Includes create_chart, create_autogenerated_dashboard, etc.

NOT exposed via MCP.
EXTERNAL Agent API Tools
HTTP endpoints with defendpoint + :tool metadata in agent_api/api.clj. Auto-discovered by MCP manifest generator. Currently 8 read-only tools.

This is what we extend.
3 - The Auto-Discovery Trick
The elegant part. Adding a defendpoint with :tool and :scope metadata is all that's needed. Three separate systems auto-discover from the same source - no manual registration anywhere. This means our two new tools need changes in exactly one file for the core feature.
MCP Manifest
tools_manifest.clj walks all :tool-annotated endpoints and generates the MCP tools/list response. New endpoints appear automatically.
OAuth Discovery
all-agent-scopes() introspects defendpoint metadata to build the scopes_supported list for the OAuth protected-resource endpoint. New scopes appear automatically.
Scope Enforcement
The :scope key on defendpoint wraps the endpoint in enforce-scope middleware. Token scopes are checked against wildcard patterns. No registration needed.
One-file magic. Adding :tool {:name "create_question"} and :scope metabot/agent-question-create to a new defendpoint in agent_api/api.clj makes the tool appear in MCP tools/list, gets its scope in OAuth discovery, and enforces permissions on every call - all from metadata on the endpoint definition.

In-process dispatch is key. MCP doesn't make an HTTP call to the Agent API. It builds a synthetic Ring request with :token-scopes attached and calls agent-api/routes directly in-process. POST body params from the tool arguments become the request body. This is why new POST endpoints "just work" with MCP dispatch.
5 - Scope Architecture
Pre-wired and waiting. The scope agent:dashboard:create already exists in scope.clj - it was defined for the internal Metabot tools. But it was never imported into core.clj or used by any Agent API endpoint. We just need to connect the dots.
Permission-to-Scope Mapping
Enterprise Metabase maps three permission types to wildcard scope grants. The question: where does agent:question:* go?
Permission Type Grants Rationale
metabot-sql-generation agent:sql:* agent:transforms:* agent:snippets:* SQL power users
metabot-nlq agent:query:* agent:table:* agent:metric:*

6 - New Tools Design
NEW TOOL create_question
Saves a constructed query as a named question. Reuses the base64-encoded query from construct_query - the LLM never touches raw MBQL.
Required
name - question title
query - base64 from construct_query
Optional
display - chart type (default: "table")
description - human description
collection_id - target folder
visualization_settings
Scope: agent:question:create (new)   Endpoint: POST /api/agent/v1/question   Reuses: create-card! from queries/models/card.clj
NEW TOOL create_dashboard
Creates a dashboard, optionally populated with saved questions. Uses Metabase's autoplace module for intelligent card positioning on the grid.
Required
name - dashboard title
Optional
description - human description
collection_id - target folder
question_ids - array of saved question IDs
Scope: agent:dashboard:create (existing!)   Endpoint: POST /api/agent/v1/dashboard   Reuses: autoplace/get-position-for-new-dashcard
Design choice: base64 queries, not raw MBQL. The create_question tool accepts the opaque base64 string from construct_query, not a raw dataset_query map. This prevents LLMs from constructing invalid MBQL and keeps the API surface simple. The decoding path is identical to execute_query.
