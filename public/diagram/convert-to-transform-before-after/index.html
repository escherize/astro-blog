Convert Model to Transform

before & after — api redesign per alexander's feedback

Before
After

Endpoint

POST /api/ee/replacement/convert-card-to-transform

Request Body

card_id, transform_name, transform_target

Who Creates the Transform?

Backend — the endpoint creates the transform from the model's query, names it, picks the output table.

Source Entity

Cards only (must be type = "model")

Backend Phases

4 phases in one endpoint:
1. Create transform
2. Execute transform
3. Find output table
4. Replace usages

Cancellation

Only during phase 4 (replacement). Phases 1–3 run unchecked.

Endpoint

POST /api/ee/replacement/replace-source-with-transform

Request Body

source_entity_id, source_entity_type, transform_id

Who Creates the Transform?

Frontend — calls existing POST /api/transform API first. Handles naming, errors, table conflicts natively.

Source Entity

Any entity type (card or table)

Backend Phases

3 phases (transform already exists):
1. Execute/re-run transform
2. Find output table
3. Replace usages

Cancellation

Checked between every phase, plus during replacement.

Bug Fix: Race Condition in execute-async!

Fix #1 — Clean 409 on concurrent starts
Problem: execute-async! does a check-then-act: checks active-run, then calls start-run!. Two concurrent requests can both pass the check. The DB unique constraint on is_active=true catches the second, but it surfaces as a 500 (constraint violation) instead of a clean 409.

Fix: Wrap start-run! in try-catch. On constraint violation, throw a clean 409 with "A source replacement is already running". The unique constraint is the real mutex; the pre-check is just a fast-path optimization.
Fix #2 — Cancellation between phases
Problem: In the old convert-card-to-transform!, phases 1–3 (create, execute, sync) ran without checking for cancellation. A user could cancel a run, but the heavy transform execution would continue until phase 4.

Fix: Added check-canceled! calls between execute and find-table, and between find-table and replace. Uses replacement.protocols/canceled? which polls the DB for the run's is_active status.
Progress model unchanged. Progress stays null during transform execution/sync (where we can't meaningfully track it), then tracks 0→1 during source replacement — same granularity as a regular replace run.
