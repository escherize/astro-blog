How MCP hooks into ai-benchmarks

The more-mcp-tools branch of Metabase ships write-capable tools at /api/mcp. mcp_bench is the harness that drives those tools with one or more LLMs and scores the side effects.

02 Runtime architecture · per-spec, per-model

Three layers, one chat loop

mcp_bench sits in the middle. It pulls the live tool list from Metabase, hands the OpenAI-shaped schemas to whichever LLM the user picked, then proxies tool calls back to /api/mcp. After the loop, metrics check Metabase's actual state.

LLM layer

litellm.acompletion

benchmarks/mcp_bench/llm_adapter.py

One call site fits every provider. Pass anthropic/claude-sonnet-4-6 or openai/gpt-4o as the model string and the SDK normalizes the request.

  • Auth keys lifted from benchmark_lib.config.env
  • MCP tools fed as OpenAI tools=[...] dicts
  • Each --runner flag adds another model to the matrix

mcp_tools_to_openai

function in llm_adapter.py

Translates MCP's {name, description, inputSchema} into OpenAI's {type:'function', function:{...}}. Same JSON schema, different envelope.

mcp_bench (this repo)

runner.run_spec_for_model

benchmarks/mcp_bench/runner.py

The chat loop. Up to MAX_TURNS=10. On each turn:

  • Call LLM with current message history
  • If LLM emits tool_calls, dispatch each through MCP
  • Feed tool results back as role:tool messages
  • Stop when LLM responds without tool calls

MetabaseMCPClient

benchmarks/mcp_bench/mcp_client.py

JSON-RPC 2.0 over Streamable HTTP. Handles both application/json and SSE (text/event-stream) responses.

  • tools/list for live schema fetch
  • tools/call for invocation
  • Side-channel /api/collection for verification

03 Auth gotcha · two session IDs, not one

Cookie auth + MCP session

The MCP server demands two separate identifiers on every request. Skip either one and you get a -32600 Missing Mcp-Session-Id header or a 401 from Metabase auth.

Every /api/mcp request needs both headers

The first is Metabase's existing cookie session. The second comes back in the response headers of the very first initialize RPC. The client captures it from response headers and replays it on all subsequent calls.

HEADER 1 · METABASE AUTH
X-Metabase-Session: <uuid>
From POST /api/session w/ username + password
HEADER 2 · MCP PROTOCOL
Mcp-Session-Id: <uuid>
From initialize response headers; reused on all RPCs
04 Chat loop · sequence diagram

One spec, one model, up to ten turns

Each spec is a single user prompt with expected side effects. The runner streams the prompt through the chat loop, dispatching any tool calls the LLM emits. The loop ends when the LLM stops calling tools or hits MAX_TURNS. 

sequenceDiagram
  autonumber
  participant U as runner
  participant L as LLM (litellm)
  participant M as MCP /api/mcp
  participant DB as Metabase + Postgres

  U->>M: initialize (capture Mcp-Session-Id)
  M-->>U: serverInfo + session id
  U->>M: tools/list
  M-->>U: [create_collection, update_question, ...]
  U->>L: system prompt + user prompt + OpenAI tools
  loop until LLM stops calling tools (max 10 turns)
    L-->>U: assistant message + tool_calls
    par dispatch each tool call
      U->>M: tools/call {name, arguments}
      M->>DB: side effect
      DB-->>M: result
      M-->>U: content blocks
    end
    U->>L: tool results as role:tool messages
  end
  L-->>U: final assistant message (no tool calls)
  U->>M: list_collections (verify side effect)
  M->>DB: SELECT
  DB-->>M: rows
  M-->>U: collection list
  Note over U: score: tool_called + collection_created
05 Scoring · per-spec metrics

Two kinds of checks, separated on purpose

Splitting "did the LLM call the right tool" from "did the side effect actually happen" makes it cheap to tell apart tool-discoverability bugs from server-side bugs.

tool_called
SYNC · transcript only

Did the LLM pick the expected tool?

Walks the transcript and looks for the expected tool_calls[*].name. Doesn't touch Metabase. Cheap, deterministic, runs in milliseconds.

If tool_called fails and the spec was reasonable → tool description / discoverability problem in MCP, not server bug
collection_created
ASYNC · hits Metabase

Did the side effect actually happen?

After the chat loop, calls GET /api/collection and checks that a collection with the rendered name exists. Confirms the write actually landed.

If tool_called passes but collection_created fails → tool implementation bug or args wrong on the LLM side
06 Output · per-model + aggregate

Scores break down two ways

Per-model so you can see which LLM nails which tool. Aggregate so you can score the tool surface as a whole — "across all the models we care about, what % of create_collection attempts succeed?"

summary.json

results/<ts>/summary.json

Per-model pass/fail counts and rates per metric, plus an overall (mean of per-metric rates). Same shape for the aggregate across all runners.

  • per_model[model][metric] = {pass, fail, rate}
  • per_model[model].overall = mean(rates)
  • aggregate[metric] + aggregate.overall

summary.md

results/<ts>/summary.md

Human-readable markdown table. Rows are models + an aggregate row. Columns are metrics + an Overall column. Each cell shows pass/total (rate%).

Full transcripts and per-spec scores land in results/<ts>/runs/<model_slug>/<spec>.json for after-the-fact inspection.
