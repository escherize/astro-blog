Parallel Agent
Work Queue

A pattern for parallelizing large mechanical refactors across multiple AI subagents
SQLite work queue · Babashka scripts · Pipeline stages · Audit trail

1 — The Problem

Many codebase refactors are intellectually trivial but volumetrically huge. Consider replacing a keyword access pattern like (:details db) across hundreds of files. 95%+ of changes are mechanical, but the remaining 5% require human judgment.


The traditional approach forces synchronous babysitting: you sit with the AI agent, processing files one at a time, watching it work, correcting mistakes. The agent speeds you up, but you're still the bottleneck because your time budget limits throughput, not the complexity.

2 — Solution Architecture
Core Idea

Turn a sequential human workflow into a parallelizable, async-reviewable pipeline. Use a SQLite database as a shared work queue. Babashka scripts provide atomic claim/complete operations. Multiple subagents process units of work simultaneously, each with narrow, focused context. The human reviews results after the fact - not in real time.

db SQLite Work Queue
Central database with state machine per work unit. Rows represent files/locations to process. Agent-ID on claims detects orphaned work.
bb Babashka Scripts
Atomic operations: claim-work.bb, complete-work.bb, advance-stage.bb. Each agent calls these to manage its lifecycle.
log Rationale Columns
Every agent decision is recorded. Complete audit trail from final product back through pipeline stages to the original input.
imm Append-Only Data
Completing one stage inserts rows into the next stage's checklist. Data is effectively immutable - full history is always reconstructable.
3 — State Machine
Each work unit progresses through a simple state machine. The agent-id is stored on claim so that orphaned work (agent crashed, timed out) can be detected and re-queued. Completing a unit in one stage atomically creates an entry in the next stage's table.

          U["Unclaimed"]
          C["Claimed"]
          P["Processing"]
          D["Done"]
          F["Flagged"]

CREATE TABLE work_items (
  id          INTEGER PRIMARY KEY,
  file_path    TEXT NOT NULL,
  stage        TEXT NOT NULL,        -- 'classify', 'transform', 'review'
  status       TEXT NOT NULL,        -- 'unclaimed', 'claimed', 'done', 'flagged'
  agent_id     TEXT,              -- which agent claimed this
  claimed_at   TIMESTAMP,
  rationale    TEXT,              -- agent's reasoning
  result       TEXT                -- what was done
);
4 — Pipeline Stages
Multi-Stage Pipeline

Work flows through distinct stages, each with its own focused prompt and validation criteria. A stage that's purely mechanical can run with less oversight than one requiring judgment. Completing one stage inserts rows into the next.

Stage Isolation
Each stage gets its own prompt, tailored to that specific task. Stage 2 classifies, Stage 3 transforms. Narrow context = better agent performance.
Prompt Per Stage
Instead of "refactor everything", each agent gets: "Analyze this one file. Is this :details access mechanical or special? Record why."
5 — Metabase Example
The :details Keyword Refactor

The writable-connections feature required replacing ubiquitous (:details db) keyword access with a new abstraction layer. Hundreds of files, mostly mechanical, but some edge cases where :details was used as a map key or in select-keys.

Setup (30 min)
Claude writes the SQLite schema, babashka scripts, and per-stage prompts. Disposable infrastructure - bespoke to this specific refactor.
Populate (5 min)
grep -r ":details" --include="*.clj" finds all candidates. One row per file inserted into the work queue.
Classify (parallel)
12 subagents each claim one file at a time. Classify each :details usage: "standard accessor" vs "map key in select-keys - flag for review".
Transform (parallel)
Agents take all "mechanical" items and apply the transformation. (:details db) becomes (mi/details db). Rationale recorded for each change.
Review (async, human)
Next morning: review git diff for mechanical changes. Work through flagged items manually. Complete audit trail for every decision.
6 — Metabase Subagent Roster
Claude Code Integration

The work queue pattern maps directly onto Claude Code's Agent tool. The orchestrator (your main session) creates the SQLite DB and bb scripts, then spawns domain-specific subagents via subagent_type. Each agent runs in the background with run_in_background: true and optionally in an isolated worktree to prevent file conflicts.

Agent selection matters. A refactor touching query processor code should use mbql-expert, not platform-expert. The domain knowledge baked into each agent's system prompt means it understands the intent behind the code it's changing, not just the syntax.

platform-expert
App DB, HTTP server, API framework, settings, migrations, caching, Toucan 2 models. Use for refactors touching api/, server/, models/.
mbql-expert
Query processor, MBQL, SQL compilation, driver system, HoneySQL, middleware pipeline. Use for refactors in query_processor/, driver/.
content-expert
Collections, cards, dashboards, models, metrics, revisions, bookmarks. Use for refactors touching content entity code.
permissions-expert
Data access, sandboxing, SSO, session management, embedding security. Use for refactors touching auth or permission checks.
drivers-and-sync
Database drivers, metadata sync, fingerprinting, type mapping, connection management. Use for driver-specific refactors.
enterprise-expert
Serialization, audit, SCIM, multi-tenancy, premium features. Use for refactors in metabase_enterprise/.
Orchestration Pseudocode
-- 1. Orchestrator populates the queue
bb populate-queue.bb  -- grep + classify files by domain

-- 2. Spawn agents per domain
Agent(subagent_type="platform-expert",
  run_in_background=true,
  isolation="worktree",
  prompt="Run claim-work.bb in a loop.
    For each claimed file, apply the
    refactor. Record rationale via
    complete-work.bb. Stop when no
    unclaimed items remain.")

-- 3. Repeat for each domain expert...
-- 4. Human reviews when notified
Domain routing. The populate step can auto-classify files by path: src/metabase/query_processor/ routes to mbql-expert, src/metabase/api/ routes to platform-expert, etc. Files that span domains get flagged for manual assignment or the general-purpose agent.
7 — Before vs After
Traditional: Sequential
New: Parallel Work Queue
  • Human processes files one at a time
  • Must babysit agent synchronously
  • Context switches between mechanical and tricky cases
  • No audit trail of reasoning
  • Throughput limited by human attention
  • Large refactors often abandoned due to time budget
  • 12 agents process files simultaneously
  • Human reviews results asynchronously
  • Mechanical work separated from judgment calls
  • Full audit trail for every decision
  • Throughput limited only by parallelism
  • Can run overnight, review in the morning

8 — Key Properties
Narrow Context
Each agent sees one file + a focused prompt. Smaller context windows mean fewer hallucinations and more reliable output.
File-Level Locking
No more than one agent per file. Claim atomicity prevents conflicts and merge disasters.
Audit Trail
Rationale columns record agent reasoning at every stage. Trace any final result back through the full pipeline.
Async Human Review
Review isn't synchronous with execution. Let agents run overnight, review git diff and flagged items the next morning.
Disposable Infrastructure
~30 minutes for Claude to write the tools. Scripts are bespoke to each refactor. The pattern is reusable, not the code.
Orphan Detection
Agent-ID on claims + timestamps enable detection of crashed or timed-out agents. Orphaned work gets re-queued automatically.
When this pattern fits: Large mechanical refactors, codemod-like changes where grep finds candidates but each needs contextual understanding, audit/inventory tasks. When it doesn't: Tightly-coupled changes where file A determines file B, architectural refactors where the design emerges as you go, anything requiring whole-picture context.
Origin: Pattern developed by Timothy while building a topical index for 1050 pages of 18th-century Latin text (13 categories, 27K items). Adapted for software engineering refactors in the Metabase codebase.
