Overview

dangerous-claude wraps Claude Code in a Docker container so you can run --dangerously-skip-permissions without exposing your entire filesystem. You specify which directories to mount - everything else is invisible to the agent.

5 stars on GitHub. MIT licensed. Single-author project (MattFlower). Last updated Jan 18, 2026. Honest about limitations - the README explicitly documents what is and isn't protected.

Container Architecture
Base Image
Ubuntu 24.04 with Node.js 20.x LTS, Docker CLI, ripgrep, fd, jq, git
Claude Code
@anthropic-ai/claude-code installed globally via npm. Auto-updates on each start.
SDKMAN Tooling
Optional: Java 21 (Zulu), Gradle, Maven. Configurable via sdkman.txt.
Entrypoint
Runs as root for UID/GID mapping + overlay setup. Drops to claude user via gosu.
privilege boundary

After entrypoint: All Claude Code activity runs as the non-root claude user with --security-opt no-new-privileges preventing re-escalation. The working directory is /workspace/<dirname>.

Security Model
Protected
  • Host filesystem invisible (only mounted dirs)
  • ~/.gradle, ~/.m2 overlay-protected
  • ~/.gitconfig mounted read-only
  • no-new-privileges blocks escalation
  • Credentials written with atomic ops + symlink checks
Exposed / Risks
  • Mounted project dirs: full read-write
  • ~/.claude dir: read-write, no overlay
  • Full outbound network access
  • Docker socket (if --docker flag used)
  • CAP_SYS_ADMIN during entrypoint phase
  • Env vars (API keys, tokens) accessible inside
Notable Concerns
  • CAP_SYS_ADMIN is granted by default for overlay mounts - powerful capability, mitigated by privilege drop
  • npm update -g runs on every start before interaction - supply chain attack surface
  • Docker socket access via --docker is effectively host root access
  • curl-pipe-bash installer - standard risk, but the script just does git clone
Overlay Filesystem

Cache directories (~/.gradle, ~/.m2) are protected using Linux overlayfs. Writes go to an ephemeral layer; host files are untouched. On container restart, changes vanish.

Host ~/.m2
→

→
Merged View
/home/claude/.m2
Key invariant: Deletions only affect the upper layer. If Claude runs rm -rf ~/.m2/*, the host directory is untouched. On next container start, everything reappears. Use --no-overlay to disable this (writes persist to host, but no deletion protection).

Credential security details
One-time seed only. Keychain sync only writes if the file doesn't exist or has invalid JSON. Once a valid file exists, it's never overwritten from Keychain - because the container may have refreshed the token, and it can't write back to Keychain.

Safety measures: symlink check before write, chmod 600 on temp file before writing data, mkdir-based file lock with stale lock detection (60s timeout), JSON validation via jq, atomic mv to final location.

Audit Summary
Aspect Rating Notes
Filesystem isolation Good Only mounted directories visible inside container
Network isolation None Full outbound access - can exfiltrate data from mounted dirs
Privilege model Decent CAP_SYS_ADMIN + drop to non-root + no-new-privileges
Credential safety Decent Careful code, but creds on disk and in env vars
Code quality Good Clean bash, proper error handling, good comments
Documentation Excellent Honest about limitations - rare for security tooling
Bottom line: A solid, honest project that does what it claims. Meaningful improvement over running --dangerously-skip-permissions on bare metal. Main gaps are network isolation and CAP_SYS_ADMIN. Good for individual developers who want autonomy with guardrails. Not a replacement for proper infrastructure sandboxing in team/production contexts.
