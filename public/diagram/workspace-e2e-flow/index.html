workspace-full-e2e-test — what it does

Stands up a real warehouse + Metabase Database, provisions an isolated workspace, runs a transform whose target gets rewritten to the isolation schema, then asserts that the canonical input schema is the only thing visible from Metabase’s perspective. Runs once per driver in workspaces-supported-dwh-drivers.

Why this test exists the “lie” model

Workspace mode says: :model/Table rows always live at the canonical identity (e.g. main_schema.orders); isolation is a physical-storage detail revealed only at driver-call boundaries. Sync, describe-database, and the data-picker all see the canonical names. The warehouse sees the remapped iso.orders.

A driver can break this in dozens of subtle ways: leaking the iso schema into :model/Table, retiring canonical Tables that have no warehouse backing, populating the iso DB into :db on the connection. The e2e flexes every layer at once so any leak shows up as a single red assertion.

The transform redirect load-bearing

The transform’s :target points at the canonical main_schema.output-table-name. The workspace transform-hook rewrites :schema to the isolation schema before dispatch. So the warehouse sees INSERT INTO iso.<name>; the app-db :model/Table stays at (main-schema, name).

The pre-seeded canonical output table is the trap. It exists with rows (99 pre-existing) (98 still-pre-existing). If the redirect ever fails, the transform overwrites those rows. The final admin-spec SELECT proves it didn’t.

What each Card asserts three angles

MBQL on canonical Table id — routes through the QP and the workspace remap middleware. Returns the iso rows.

Native on iso schema — user typed the iso name themselves; the QP shouldn’t touch it. Returns the iso rows.

Native on canonical schema — user typed the canonical name; the SQL rewriter swaps it. Returns the iso rows.

Cleanup ordering fragile but correct

The inner finally at e2e_test.clj:490 does three things in order: clear the workspace atom, restore admin creds on :model/Database, then call ws/delete-workspace!. Restoring admin creds is critical — the loader rewrote :details to workspace-user creds, but destroy-workspace-isolation! needs admin to drop the iso role and user. Skip this step and the destroy throws, the WSD stays provisioned, and mt/with-temp’s Database delete throws because of the :model/Database before-delete hook.

Why it’s a single deftest, not split. The provisioning state and the workspace-instance-config atom are both process-wide; splitting the test into smaller deftests would force each to redo the full initialize! + provision dance, multiplying runtime against the warehouse. ^:synchronized protects the atom from cross-test pollution within the JVM. The driver loop (mt/test-drivers) is the only thing that runs the body multiple times.
