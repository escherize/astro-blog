Metadata Provider

metabase.lib.metadata.protocols — cross-platform abstraction for schema metadata

1 — What It Is

The metadata provider is a cross-platform Clojure protocol (.cljc) that gives any consumer — the Query Processor, MLv2, tests — a uniform interface to ask questions about the structure of a data warehouse: its tables, columns, saved questions, segments, metrics, and more.

It doesn't matter where the metadata lives — an application database, a Redux store, or a hand-crafted test map. The protocol abstracts over all sources so callers never need to know.

2 — The Problem It Solves

Metabase needs schema metadata in three very different contexts, each with a different data source:

Server-side (JVM)
The Query Processor compiles MBQL to SQL. It needs table/field metadata to resolve references, add joins, check types.
Source: App DB
Client-side (CLJS/JS)
MLv2 runs in the browser to build queries interactively. No direct DB access — metadata comes from the Redux store or REST API.
Source: Redux / REST
Tests
Unit tests fabricate metadata without any database at all. Provider is a plain Clojure map.
Source: Mock maps
One protocol, many backends. Code that asks "what are the fields in table X?" doesn't care whether the answer comes from a SQL query, a cached REST response, or a test fixture.
3 — Core Protocol

MetadataProvider
database(provider) → DatabaseMetadata
metadatas(provider, spec) → [metadata-objects...]
setting(provider, key) → setting-value

metadatas is the workhorse. It takes a spec map with :lib/type (e.g. :metadata/table, :metadata/column) plus optional filters (:id, :name, :table-id). All convenience helpers — lib.metadata/table, lib.metadata/field, lib.metadata/card — are built on top of metadatas.

5 — Provider Implementations

Production Backend Stack (JVM)

Three decorators wrap around each other, outermost first:

Outer InvocationTracker
Tracks which card IDs were accessed during query execution. Powers card.last_used_at updates.
↓
Middle CachedProxyMetadataProvider
Atom-based cache with ::nil tombstones for misses. Splits requests into cached vs. missing IDs, fetches only what's needed.
↓
Inner UncachedApplicationDatabaseMetadataProvider
The real data source. Queries the Metabase application database via Toucan 2. Translates metadata specs into HoneySQL WHERE clauses, joins Field with Dimension and FieldValues.
ComposedMetadataProvider
Chains N providers left-to-right. Deduplicates by ID. Provider 1 can shadow (delete) items from provider 2.
BootstrapMetadataProvider
Minimal provider to resolve database ID for virtual DB queries (card__N sources) before the real provider exists.
MockMetadataProvider
For tests. Holds a plain map: {:database ..., :tables [...], :fields [...]}. No database required.
6 — How a Field Lookup Works 
        graph TD
          A["lib.metadata/field provider 42"] --> B["protocols/metadatas"]
          B --> C["InvocationTracker"]
          C -->|"records field 42"| D["CachedProxyMetadataProvider"]
          D --> E{"Cache hit?"}
          E -->|"HIT"| F["Return cached result"]
          E -->|"MISS"| G["UncachedAppDBProvider"]
          G --> H["metadata-spec to HoneySQL"]
          H --> I["t2/select joins Field + Dimension + FieldValues"]
          I --> J["instance to metadata: snake_case to kebab-case + :lib/type"]
          J --> K["Store in cache under :id and :name keys"]
          K --> F
Cache warming. QP middleware like resolve-fields knows upfront which field IDs a query references. It calls bulk-metadata to fetch them all in one SQL query instead of one-by-one.
7 — Three Layers of Caching
Layer 1 Request-Scoped Provider Cache
HTTP middleware binds *metadata-provider-cache* per request. Same provider instance is reused for the same database-id within one HTTP request. A dashboard loading 5 cards from the same DB creates just 1 provider.
Layer 2 Per-Provider Object Cache
Each CachedProxyMetadataProvider holds an (atom {}). On fetch, it splits requested IDs into "cached" vs "missing", fetches only missing, stores ::nil tombstones for not-found items, and caches under both :id and :name keys simultaneously.
Layer 3 General Computed Value Cache
cached-value / cache-value! for arbitrary computed results (e.g. visible-columns). Replaces the deprecated qp.store/cached macro. Middleware can cache expensive computations for the duration of a query.

The bridge: During sync, Metabase introspects the warehouse schema and writes it to app DB tables. The metadata provider then serves this cached structural info so the QP doesn't need to introspect the warehouse at query time.
