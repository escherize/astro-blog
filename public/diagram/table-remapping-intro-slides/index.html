The Rule

A routing rule at the SQL boundary.

On database D, when something asks for
canonical-db.canonical-schema.canonical-table
→ serve them from
target-db.target-schema.target-table.
  • Above the boundary — cards, dashboards, pickers, serdes — the world is canonical.
  • Below the boundary — warehouse SQL, JDBC describe — the world is target.

The whole primitive, in one row.

:model/TableRemapping 
{:database-id  7

 :from {:db     ""
        :schema "public"
        :table  "orders"}

 :to   {:db     ""
        :schema "ws_alice"
        :table  "orders"}}

;; That's it. No user, no role, no workspace field.
;; Anything that wants identity routing produces this row.

Phase 1

preprocess · MBQL only

Flip the metadata provider.

  • Walk the active remappings; for each, mutate :metadata/table to the target identity.
  • MBQL tree untouched. HoneySQL reads the mutated identity at compile time.
  • Provider is the single chokepoint — covers :source-table, joins, field-refs, implicit joins, everything.
  • Runs after sandboxing — filters materialize against canonical first, then identity flips.

Phase 2

execute · native & compiled SQL

Rewrite the compiled SQL.

  • Parse :qp/compiled with SQLGlot via GraalPy → 3-tuples.
  • Match against active remappings → sql-tools/replace-names.
  • Throws on parse fail. Never silent fallback to canonical.
  • Corpus-validated: 12,511 queries across 7 dialects · 0 errors.

Disambiguation

What it isn't.

Table remapping is a fourth axis, orthogonal to existing routing primitives. The naming overlaps; the mechanics don't.

→ Table remapping
Same connection, different SQL. Per database × table tuple.
Field remapping
Stored value → display value in result rows. Different word, different code.
Sandboxing
Rewrites query shape. Per user. Remap rewrites idents in unchanged shape.
DB Routing
Same SQL, different connection. Mutually exclusive with remap on the same DB.
Source-replacement
Mutates card content in app DB. Remap leaves content untouched, rewrites at boundary.
