Async Dependency Handlers

metabase-enterprise.dependencies — card save event pipeline

When a card is saved, three event handlers fire from publish-event! :event/card-update. Two of them are expensive and were blocking the HTTP response for minutes on large instances. Now they run asynchronously on a dedicated executor thread.

The Three Handlers

What fires on :event/card-update, and what changed

Before — all synchronous
After — cheap sync, expensive async

All three handlers ran inline on the request thread. The PUT response couldn't return until every handler completed:

  1. ::card-deps sync Recalculate upstream deps for the saved card O(1) — cheap
  2. ::check-card-dependents sync Upsert analysis + mark all dependents stale O(n) dependents — moderate
  3. ::update-card-dependents-metadata sync Infer metadata for every MBQL dependent card O(n) × query cost — expensive

The cheap handler stays inline. The two expensive ones submit work to a single-threaded executor:

  1. ::card-deps sync Unchanged — still inline, still fast O(1) — cheap
  2. ::check-card-dependents async Wrapped in async/submit! runs on executor thread
  3. ::update-card-dependents-metadata async Wrapped in async/submit! runs on executor thread

Before: Blocking Timeline

PUT /api/card/:id — response blocked until all handlers complete

sequenceDiagram
    participant FE as Frontend
    participant API as PUT /api/card
    participant DB as Database
    participant H1 as card-deps
    participant H2 as check-card-dependents
    participant H3 as update-dependents-metadata

    FE->>API: PUT card save
    API->>DB: UPDATE card row
    DB-->>API: committed

    Note over API,H3: publish-event! :event/card-update

    API->>H1: inline call
    H1->>DB: replace-dependencies!
    DB-->>H1: done
    H1-->>API: done (fast)

    API->>H2: inline call
    H2->>DB: upsert-analysis!
    H2->>DB: mark-dependents-stale! (n rows)
    DB-->>H2: done
    H2-->>API: done (moderate)

    API->>H3: inline call
    loop Each MBQL dependent (n cards)
        H3->>DB: infer-metadata + update
    end
    H3-->>API: done (SLOW)

    Note over API: NOW response can return
    API-->>FE: 200 OK
The problem. The save itself commits in milliseconds. But the PUT handler waits for all three event handlers to complete before returning the HTTP response. With 2,075 dependents, ::update-card-dependents-metadata takes minutes to infer metadata for each one. The user sees a spinner the entire time.

PUT returns after the cheap handler; expensive work queues in background

Type

dependency-event-worker
Serialization
Tasks execute one at a time — no concurrent writes to dependent cards
Binding Capture
bound-fn* captures dynamic bindings (DB connections, user context)
Lifecycle
Daemon thread — shuts down with the JVM
Testability
with-redefs [async/submit! (fn [f] (f))] for synchronous test execution
Why single-threaded? If a user rapidly saves the same model three times, the dependency updates queue up and process in order. No concurrent writes racing to update the same dependent cards. The pattern follows metabase.util.quick-task.
