How MBQL Becomes SQL

metabase query processor · nested card compilation

When you build a question in Metabase, it becomes an MBQL query — a Clojure data structure describing what you want. When that question uses another saved question as its source, the QP must recursively resolve and inline the inner query, then compile the whole thing to a single SQL statement with subqueries. Here’s exactly how that works.

3 — Source Card Resolution

This is the heart of nested queries. When Card B uses Card A as its source, the MBQL looks like {:source-card 42}. The resolve-source-cards middleware in fetch_source_query.clj replaces that reference with Card A’s actual query stages.

Recursion & safety: If Card A itself references Card C as its source, resolve-source-cards* recurses up to 50 levels deep. It uses a dependency graph (via com.stuartsierra/dependency) to detect circular references and throws an error if found.

After resolution, the query has two stages: the first is Card A’s query (with :source-table pointing at the real DB table), and the second is Card B’s operations (filters, aggregations, etc.). The compilation step will turn this multi-stage pipeline into nested SQL subqueries.

4 — MBQL to SQL Compilation

After preprocessing, compile.clj calls driver/mbql->native, which dispatches to the SQL query processor. The compilation has two phases: MBQL → HoneySQL → SQL string.

The recursion: When the outer query has a :source-query (from the multi-stage pipeline), apply-source-query calls apply-clauses recursively on the inner query. This produces a nested HoneySQL form that format-honeysql renders as SELECT ... FROM (SELECT ...) AS "source".

The ->honeysql multimethod dispatches on [driver, clause-type], so each database driver can customize how any MBQL clause compiles to SQL. For example, Postgres, MySQL, and BigQuery all have their own temporal bucketing, string function, and type-casting implementations.

Clause application order

Top-level clauses are applied in a strict order because the SELECT clause is built progressively — breakout columns must appear before aggregation columns:

  1. :source-table → FROM
  2. :breakout → GROUP BY + SELECT
  3. :aggregation → SELECT aggregate exprs
  4. :fields → SELECT
  5. :filter → WHERE
  6. :joins → JOIN
  7. :order-by → ORDER BY
  8. :page / :limit → LIMIT / OFFSET
5 — The Final SQL

For our example — Card A selects from the ORDERS table with some fields, and Card B filters Card A’s results where TOTAL > 100 — the compiled SQL looks like this:

Compiled SQL Output
-- Card B's outer query
SELECT
  "source"."ID",
  "source"."USER_ID",
  "source"."PRODUCT_ID",
  "source"."TOTAL"
FROM (
  -- Card A's inner query (inlined as subquery)
  SELECT
    "ORDERS"."ID"     AS "ID",
    "ORDERS"."USER_ID" AS "USER_ID",
    "ORDERS"."PRODUCT_ID" AS "PRODUCT_ID",
    "ORDERS"."TOTAL"  AS "TOTAL"
  FROM "PUBLIC"."ORDERS"
) AS "source"
WHERE "source"."TOTAL" > 100
LIMIT 2000
The "source" alias: All nested subqueries are aliased as "source" (defined as source-query-alias in the SQL QP). The outer query references columns via "source"."COLUMN". If there are ambiguous column names, a WITH clause is used instead to rename them.

The result is a streaming reduction — rows flow through the post-processing middleware as transducers, so Metabase never holds the entire result set in memory. The rff (reducing function function) pattern lets each middleware layer transform rows one at a time.

7 — Performance: 10M Rows, LIMIT 1

What happens when Card A selects from a table with 10 million rows, and Card B is based on Card A with LIMIT 1? The compiled SQL is:

The 10M Row Scenario
SELECT *
FROM (
  -- Card A: no limit here! Full 10M row table.
  SELECT * FROM "PUBLIC"."BIG_TABLE"
) AS "source"
LIMIT 1

The LIMIT does not propagate into the subquery — it only appears on the outer SELECT. So how does this stay fast? There are three layers of defense, from the database all the way up to Clojure transducers.

Layer 1 — Database optimizer. Most databases (Postgres, MySQL, SQL Server, etc.) are smart enough to recognize SELECT * FROM (...) LIMIT 1 and stop the inner scan after producing one row. The subquery never materializes all 10M rows. This is the primary performance guarantee — the database does the heavy lifting.
Layer 2 — JDBC streaming. Even if the database sends more data than expected, the JDBC driver in sql_jdbc/execute.clj uses ResultSet.TYPE_FORWARD_ONLY with a configurable fetchSize. Rows arrive in small batches rather than being buffered entirely in memory. The connection is set to read-only with auto-commit enabled to avoid holding transactions open.
Layer 3 — Transducer early termination. The limit-result-rows post-processing middleware wraps the reducing function with Clojure’s (take n) transducer. After receiving 1 row, take returns (reduced acc). The reducible-rows loop in reducible.clj checks reduced? on every iteration and exits immediately. The JDBC Statement is then canceled to tell the database to stop working.

Here’s the actual code flow that makes early termination work: 

sequenceDiagram
  participant QP as Query Processor
  participant LIM as limit-result-rows
  participant RED as reducible-rows loop
  participant JDBC as JDBC ResultSet
  participant DB as Database

  QP->>DB: Execute SQL with LIMIT 1
  DB-->>JDBC: Open cursor
  QP->>RED: Start transduce
  RED->>JDBC: Fetch row 1
  JDBC-->>RED: Row data
  RED->>LIM: rf(acc, row)
  Note over LIM: take(1) counts down
  LIM-->>RED: reduced(acc)
  Note over RED: reduced? = true
  RED-->>QP: Return result
  QP->>JDBC: Statement.cancel()
  Note over DB: Database stops work
Default row limits by context

Metabase adds default limits via constraints.clj even when the user doesn’t specify one. These are the “userland constraints”:

  • Unaggregated queries: 2,000 rows (browsing a table)
  • Aggregated queries: 10,000 rows (grouped results)
  • Downloads: Configurable via download-row-limit setting
  • Subscriptions: Configurable via attachment-row-limit setting
  • Absolute maximum: 1,048,576 rows (Excel sheet limit)

The effective limit is always the minimum of the user’s explicit limit, the context-specific limit, and the absolute max. Computed by determine-query-max-rows in limit.clj.

What about persisted models?

If Card A is a persisted model (materialized to a real table via substitute-persisted-query middleware), the subquery is replaced with a direct SELECT from the cached table. The SQL becomes SELECT * FROM "metabase_cache_abcdef" LIMIT 1 — no subquery at all. This is the fastest path for frequently-used base models.
