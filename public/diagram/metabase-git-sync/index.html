Metabase Git Sync

serialization engine + remote sync — enterprise feature deep dive

Git Sync lets Metabase instances synchronize their content (dashboards, questions, collections) via a remote git repository. It's built as two layered systems: a core serialization engine that converts entities to/from portable YAML, and a remote sync layer that adds git transport, change tracking, and scheduling on top.

2 — Two-Layer Architecture
Layer 1: Serialization Engine
Core Extract / Load Pipeline
Converts Metabase entities to/from portable YAML. Stateless — no git awareness, no change tracking. Also powers the legacy v2-dump! / v2-load! CLI commands and /api/ee/serialization tar.gz export.
extract.clj load.clj storage.clj ingest.clj
Layer 2: Remote Sync
Git Integration Layer
Built on top of serialization. Adds JGit transport, event-driven dirty tracking, conflict detection, scheduling (auto-import every 5m), and a full API. The "jekyll mode" spec system defines which entities participate.
git.clj spec.clj events.clj impl.clj api.clj
3 — Serialization Engine
The make-spec Multimethod
The central registration point in src/metabase/models/serialization.clj (~900 lines). Each model defines a make-spec multimethod that declares how each field should be handled during serialization:
:copy
Pass through unchanged. Simple fields like name, description, display.
:skip
Ignored entirely. Internal IDs, timestamps, and computed fields.
:transform
Has :export and :import fns. Handles FK resolution, nesting, dates.

NanoID entity_id
Most entities. A 21-character NanoID stored in the entity_id column. Backfilled deterministically from an identity hash for pre-existing entities — same entity always gets the same ID across instances.
Natural Keys
Database (by name), Table/Field (by path). Example: ["prod-db" "public" "orders" "total"]. No entity_id needed — the path is globally unique.
Inlining
DashboardCard, DashboardTab, TimelineEvent, etc. Serialized inside their parent's YAML via the serdes/nested transformer. No independent file or entity_id.

7 — Git Integration Layer
JGit Transport
Uses the JGit Java library. Maintains a bare clone cached at /tmp/metabase-git/<sha1(url+token)>. Writes directly to the git index (no working directory). Auth via UsernamePasswordCredentialsProvider. JGit system reader is isolated to ignore host ~/.gitconfig.
Recovery
Auto-recovers from force-push ("Missing commit" error) by re-cloning the repository. The bare clone is cached in an atom across requests. No automatic retries on import/export failure — failed tasks are recorded in the DB, and auto-import naturally retries on the next schedule tick.
Spec System ("Jekyll Mode")
The remote_sync/spec.clj file (~1200 lines) is the data-driven configuration that determines which entities participate in git sync. Each spec declares:
  • Eligibility — collection-based, setting-based, or parent-table-based rules
  • Events — which CRUD events to listen for
  • Tracking — how to maintain sync state in RemoteSyncObject
  • Removal — rules for deleting entities missing from an import
Concurrency Model
On-demand imports/exports run in virtual threads (not Quartz). A cluster-wide database lock (app-db.cluster-lock) ensures exactly one task at a time across all instances. Tasks have a 50-minute timeout. Cancellation is cooperative — checked at each progress update.

Dirty tracking powers conflict prevention, not triggers. The event system maintains the RemoteSyncObject table but does not trigger imports or exports — those are either manual (API) or scheduled (Quartz auto-import). Dirty state is checked before import to warn about local changes that would be overwritten.
9 — Scheduling & API
Quartz Tasks
  • AutoImport — every 5 minutes (configurable). Compares git SHA to skip no-ops. Only runs in read-only mode with auto-import enabled.
  • RemoteSyncTableCleanup — daily at 2:29 AM. Prunes task records older than 30 days.
API Endpoints
  • POST /import — trigger import from git
  • POST /export — trigger export to git
  • GET /current-task — poll task status
  • GET /is-dirty / GET /dirty
  • GET /settings / PUT /settings
  • GET /branches — list remote branches
  • POST /cancel — cancel running task
10 — YAML File Structure
Git Repository Layout
  • collections/
  •   {eid}_{slug}/
  •     cards/
  •       {eid}_{slug}.yaml
  •     dashboards/
  •       {eid}_{slug}.yaml
  •     timelines/
  •       {eid}_{slug}.yaml
  • databases/
  •   {name}/
  •     schemas/
  •       {schema}/
  •         tables/
  •           {table}/
  •             fields/
  •               {field}.yaml
  • settings.yaml
Deterministic sorting. YAML keys are sorted alphabetically so that diffs are minimal and meaningful. The directory structure mirrors the Metabase entity hierarchy — collections contain cards, dashboards, etc. Database metadata follows a db/schema/table/field path.
