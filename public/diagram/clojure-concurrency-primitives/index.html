01 / 16

the spectrum

Three Philosophies

Java: Manual & Explicit

You get threads, locks, and volatile. Correctness is your problem. Maximum control, maximum footguns. Every shared mutable object is a potential data race.

Clojure: Pragmatic & Safe

Data is immutable by default. When you need mutation, you go through controlled gates (atoms, refs, agents) that enforce thread-safety for you. Side effects are allowed - just not the default path.

Haskell: Pure & Rigorous

Side effects are tracked in the type system via IO and ST monads. You literally cannot mutate state without the type signature declaring it. Elegant, but the learning curve and ceremony add friction.

why clojure wins

Clojure sits in the sweet spot:

  • Immutability eliminates most race conditions before they start
  • Managed references give you coordinated mutation when needed
  • Full JVM access - j.u.c. is always one import away
  • No purity tax - side effects are allowed, just not the default

Most concurrency bugs come from mutable shared state. Make data immutable, and 90% of the problem disappears. The remaining 10% gets explicit, well-designed primitives.

02 / 16

primitive #1

Real Threads

Platform threads mapped 1:1 to OS threads. Each one gets its own stack (~1MB), its own program counter, and is scheduled by the OS kernel.

Java - async logging
// A background thread that drains a log queue
Thread logger = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        String msg = logQueue.take(); // blocks
        writer.write(msg);
    }
});
logger.setName("async-logger");   // shows in thread dumps
logger.setDaemon(true);           // won't prevent JVM shutdown
logger.setPriority(Thread.MIN_PRIORITY); // yield CPU to real work
logger.start();
Clojure - async logging
(def logger-thread
  (doto (Thread.
          #(loop []
             (when-not (.isInterrupted (Thread/currentThread))
               (let [msg (.take log-queue)]
                 (.write writer msg)
                 (recur)))))
    (.setName "async-logger")
    (.setDaemon true)
    (.setPriority Thread/MIN_PRIORITY)
    (.start)))

Daemon vs Non-Daemon

Non-daemon (default): The JVM won't shut down until this thread finishes. Your main app thread is non-daemon. If you forget to stop a non-daemon thread, your process hangs forever on shutdown.

Daemon: The JVM kills it automatically when all non-daemon threads are done. Perfect for background work like logging, monitoring, cache cleanup - stuff that should just die when the app stops.

Thread Priority (1-10)

A hint to the OS scheduler about how to allocate CPU time. MIN_PRIORITY(1) means "run me when nothing else wants the CPU." MAX_PRIORITY(10) means "prefer me."

In practice, most OSes mostly ignore it. Linux's CFS scheduler treats all threads roughly equally. It matters more on Windows and real-time systems. For a logger, MIN_PRIORITY is polite - it won't steal CPU from request-handling threads.

Cached Thread Pool

When you call (future ...), Clojure submits your work to a cached thread pool. This is a pool that creates new threads on demand, reuses idle ones, and kills threads that sit idle for 60 seconds. You don't manage thread lifecycles - the pool does.

Under the hood it's Executors.newCachedThreadPool(). Good for bursty I/O work. Bad for CPU-bound work (can spawn too many threads).

03 / 16

threads vs lightweight processes

What's a "Lightweight Process"?

core.async go blocks are "lightweight processes" - they look like threads but are multiplexed onto a small fixed thread pool (8 threads by default).

OS Threads (real, ~1MB stack each) ┌──────────┐ ┌──────────┐ ┌──────────┐ │ Thread 1 │ │ Thread 2 │ │ Thread 3 │ ... (8 total) └────┬─────┘ └────┬─────┘ └────┬─────┘ │ │ │ Go blocks (lightweight, parked/resumed) ┌──┴──┐ ┌──┴──┐ ┌──┴──┐ │go-A │ │go-D │ │go-G │ │go-B │ │go-E │ │go-H │ │go-C │ │go-F │ │go-I │ ... (thousands) └─────┘ └─────┘ └─────┘ When a go block hits <! or >!, it parks (saves state) and the thread picks up another go block. No OS thread is blocked. No stack is wasted.
Example 
;; 10,000 concurrent "processes" on 8 threads
(dotimes [i 10000]
  (a/go
    (let [result (a/<! (fetch-chan i))]
      (a/>! output-chan {:id i :data result}))))

Real thread: ~1MB stack

Creating 10,000 OS threads = ~10GB of stack space. The OS scheduler also slows down with that many threads context-switching.

Go block: ~few hundred bytes

The go macro rewrites your code into a state machine at compile time. When a go block "parks" on a channel operation, it just saves a small state object. No thread is consumed while waiting.

The tradeoff

Go blocks must never do blocking I/O (like JDBC calls, HTTP requests, or Thread/sleep). If they block, they hold one of the 8 threads hostage and starve everyone else. For blocking work, use a/thread instead, which runs on a real thread.

Rule of thumb: go blocks for coordination logic, real threads for I/O.

Java 21 comparison

Virtual threads (Project Loom) solve the same problem differently. Instead of a macro rewriting your code, the JVM itself handles parking/resuming at the VM level. You write normal blocking code and the runtime makes it lightweight. Clojure can use these too via Thread/startVirtualThread.

primitive #2

Atoms

Thread-safe updates to a single independent value. The workhorse of Clojure state management.

Real example: rate limiter 
;; Track request counts per client
(def rate-limits (atom {}))

(defn allow-request? [client-id]
  (let [now   (System/currentTimeMillis)
        limit 100] ; per minute
    (->> (swap! rate-limits
           (fn [m]
             (let [entry (get m client-id
                         {:count 0 :window now})]
               (if (> (- now (:window entry)) 60000)
                 (assoc m client-id
                   {:count 1 :window now})
                 (update-in m [client-id :count]
                   inc)))))
         (get-in [client-id :count])
         (>= limit)
         not)))
How CAS actually works
Compare-And-Swap (CAS) - CPU instruction level Thread A wants to change atom from {:count 5} to {:count 6} Thread B wants to change atom from {:count 5} to {:count 6} Step 1: Both threads read current value: {:count 5} Step 2: Both compute new value: {:count 6} Step 3: CAS instruction (atomic, hardware-level): Thread A: "If value is still {:count 5}, set to {:count 6}" -> CPU says: YES, it's still 5. Swapped! Thread B: "If value is still {:count 5}, set to {:count 6}" -> CPU says: NO, it's now 6. Rejected! Step 4: Thread B retries: reads 6, computes 7, CAS succeeds. No lock. No blocking. The CPU's cache coherence protocol (MESI) ensures only one core can write at a time. This is a single x86 instruction: CMPXCHG.
Java AtomicReference
AtomicReference<Map> counter = new AtomicReference<>(Map.of("count", 0));

// updateAndGet does the read-compute-CAS-retry loop for you
counter.updateAndGet(m -> {
    var copy = new HashMap<>(m);
    copy.put("count", (int) copy.get("count") + 1);
    return Map.copyOf(copy); // must return immutable!
});

In Java, you have to manually copy and re-freeze the map because Java maps are mutable. In Clojure, all data is already immutable, so swap! just works - the old value is never corrupted because nobody can mutate it.

primitive #3

Promises

A write-once, read-many synchronization point. One thread delivers a value; any number of threads can block waiting for it. It's a rendezvous.

How delivery works internally
Promise internals (simplified) A promise is a small object with: - value: the delivered result (initially empty) - latch: a CountDownLatch(1) @p (deref): 1. Check if value is set -> return immediately 2. Otherwise: latch.await() -> thread parks (OS-level) The thread is removed from the run queue. It consumes zero CPU while waiting. (deliver p "result"): 1. CAS the value field (only first deliver wins) 2. latch.countDown() -> wakes ALL waiting threads OS moves them back to the run queue. After delivery, @p returns instantly forever. The latch is never checked again.
Fan-out pattern
;; One computation, many consumers
(def config-loaded (promise))

;; Three threads all waiting for config
(future (start-web-server @config-loaded))
(future (start-worker-pool @config-loaded))
(future (start-metrics @config-loaded))

;; Eventually, the config loader delivers
(deliver config-loaded (load-config!))
;; All three threads unblock simultaneously
Java equivalent
CompletableFuture<Config> cfg =
    new CompletableFuture<>();

// Consumers
cfg.thenAcceptAsync(c -> startWeb(c));
cfg.thenAcceptAsync(c -> startPool(c));
cfg.thenAcceptAsync(c -> startMetrics(c));

// Or blocking: cfg.get()

// Producer
cfg.complete(loadConfig());

// Java's version is much richer: thenApply,
// thenCompose, exceptionally, allOf, anyOf...
// It's a full async pipeline framework.

Java: very common

CompletableFuture is used heavily in Java. It's their main async abstraction - Spring WebFlux, async HTTP clients, and database drivers all return them. Java developers chain operations with thenApply/thenCompose like a monad.

Clojure: rarely used

Clojure promises are simple and intentionally minimal - just deliver + deref. No chaining, no error handling, no composition. Most Clojure devs reach for future (which handles the computation itself) or core.async channels (which are richer). Promises fill a niche: "I need to hand a value from point A to point B, once." That's it.

If you need chaining, use manifold.deferred - a Clojure library that's basically CompletableFuture done right.

primitive #4

Futures

Compute a value asynchronously. The body runs on a thread pool; deref the result when you need it. The most common concurrency primitive in Clojure.

Java
ExecutorService pool = Executors.newCachedThreadPool();

Future<String> f = pool.submit(() -> {
    return httpClient.send(request).body();
});

String result = f.get();          // blocks forever
String result = f.get(5, SECONDS); // with timeout
Clojure - parallel API calls
;; Fetch 3 APIs concurrently - total time = max(3)
(let [users    (future (http/get "/api/users"))
      orders   (future (http/get "/api/orders"))
      products (future (http/get "/api/products"))]
  ;; All 3 are running right now on separate threads.
  ;; Deref blocks until each one completes.
  {:users    @users
   :orders   @orders
   :products @products})

;; Check without blocking
(realized? users) ;=> true/false

;; Timeout: return :timeout after 5s
(deref users 5000 :timeout)

Future vs Promise

Future: owns its computation. You give it code, it runs it, you get the result.

Promise: just a mailbox. Someone else delivers the value. The promise doesn't do any work itself.

Internally, a Clojure future IS a promise (backed by java.util.concurrent.FutureTask). The future macro submits a FutureTask to the cached thread pool, and deref calls .get() on it.

Gotcha: exceptions

If the future's body throws, the exception is captured silently. It only re-throws when you deref. If you never deref, the error vanishes.

;; This error is invisible!
(future (throw (Exception. "boom")))

;; Only surfaces on deref:
@(future (throw (Exception. "boom")))
;; => ExecutionException: boom

primitive #5

Locks

Mutual exclusion. Only one thread enters the critical section at a time. The bluntest tool - use when nothing else fits.

Where does the lock "live"?
Lock = shared object on the heap Both threads have a reference to the same lock object. The lock has internal state: owner thread + count. Thread A Thread B │ │ ├─ .lock() ─────────┐ │ │ acquired! ◄──────┘ │ │ owner = A ├─ .lock() ────┐ │ doing work... │ BLOCKED ◄────┘ │ ... │ (OS parks thread, ├─ .unlock() │ zero CPU used) │ owner = none │ │ ├─ acquired! │ │ owner = B │ ├─ .unlock()
Real example: database migration lock
;; Only one thread should run migrations at startup
(def migration-lock (Object.))

(defn run-migrations! [db]
  (locking migration-lock  ; synchronized block
    (when-not (migrations-done? db)
      (log/info "Running migrations...")
      (jdbc/execute! db ["CREATE TABLE IF NOT EXISTS..."])
      (jdbc/execute! db ["ALTER TABLE..."])
      (mark-migrations-done! db))))

;; Multiple web server threads call this at startup.
;; Only the first one runs migrations.
;; The rest block, then see migrations-done? = true.

What is "reentrant"?

A reentrant lock can be acquired again by the thread that already holds it. It keeps a count.

// Thread A already holds the lock
lock.lock();   // count = 1
  lock.lock(); // count = 2 (same thread, OK!)
  lock.unlock(); // count = 1
lock.unlock();   // count = 0, released

Without reentrancy, if method A holds a lock and calls method B which also needs the lock - deadlock. The thread blocks waiting for itself.

Other Java lock types

  • ReentrantReadWriteLock - multiple readers OR one writer. Great for caches.
  • StampedLock - optimistic reads (try reading without locking, verify after). Fastest for read-heavy workloads.
  • synchronized - built into every Java object. Simpler but less flexible than ReentrantLock (no tryLock, no fairness).
  • Semaphore - not exactly a lock, but limits concurrency to N threads (see appendix).

Why use locks over atoms?

Atoms retry - so your swap function must be pure (no side effects). If your critical section writes to a database, writes to a file, or sends a network request, retrying would do it twice. Locks run the body exactly once.

primitive #6

Queues

Thread-safe data structures for passing work between producers and consumers. The backbone of pipeline architectures.

PersistentQueue - a red herring?

Clojure does have clojure.lang.PersistentQueue - an immutable FIFO queue. But it's a data structure, not a concurrency primitive.

(def q (conj clojure.lang.PersistentQueue/EMPTY
            :a :b :c))
(peek q)  ;=> :a
(pop q)   ;=> #queue[:b :c]

You could wrap it in an atom: (swap! q-atom pop). But you lose blocking behavior - a consumer can't "wait for the next item." You'd have to busy-poll. That's why BlockingQueue and core.async channels exist.

Java BlockingQueue
BlockingQueue<Job> q = new LinkedBlockingQueue<>(100);

// Producer thread - blocks if queue is full (backpressure)
q.put(new Job("process-order-123"));

// Consumer thread - blocks if queue is empty
Job job = q.take();  // thread sleeps until work arrives
process(job);
Clojure - core.async pipeline
(require '[clojure.core.async :as a])

;; Channels are like BlockingQueues with superpowers
(def jobs    (a/chan 100))  ; buffered channel
(def results (a/chan 100))

;; 4 parallel workers consuming jobs
(a/pipeline 4 results
  (map process-job) jobs)

;; Producer
(a/go
  (doseq [order orders]
    (a/>! jobs order)) ; park if buffer full
  (a/close! jobs))

;; Channels can also: select (alt!), timeout,
;; transduce, split, merge, pub/sub
Or just use Java directly
(import '[java.util.concurrent LinkedBlockingQueue])

(def q (LinkedBlockingQueue. 100))
(.put q "job")   ; blocks if full
(.take q)        ; blocks if empty

;; Perfectly fine for simple producer-consumer.
;; Use core.async when you need go blocks,
;; select, or complex pipeline topology.

primitive #7

Cyclic Barriers

A synchronization point where N threads wait for each other. When all arrive, they all proceed. Then the barrier resets and can be reused.

CyclicBarrier(3) - three threads must sync Worker A Worker B Worker C │ │ │ ├─ phase 1 │ │ ├─ await() ├─ phase 1 │ │ waiting... ├─ await() ├─ phase 1 │ waiting... │ waiting... ├─ await() │ │ │ ╞═══════════════╪═══════════════╡ ALL 3 ARRIVED! │ │ │ barrier resets ├─ phase 2 ├─ phase 2 ├─ phase 2 ├─ await() ... ... │ waiting... (cycle repeats)
Example: parallel matrix row computation
(import '[java.util.concurrent CyclicBarrier])

;; 4 workers compute their chunk of a matrix,
;; then sync so everyone sees all results
;; before starting the next iteration.
(def barrier (CyclicBarrier. 4
              #(println "iteration complete")))

(dotimes [worker-id 4]
  (future
    (dotimes [iter 100]
      (compute-rows! matrix worker-id)
      (.await barrier))))

CountDownLatch explained

Asymmetric means the threads have different roles:

CountDownLatch(3) Counters (count down): Worker A: done! countDown() -> 2 Worker B: done! countDown() -> 1 Worker C: done! countDown() -> 0 Waiters (block until 0): Main thread: await() -> unblocked!

The counters and waiters are different threads with different jobs. That's asymmetric. With a CyclicBarrier, everyone is a peer - everyone waits, everyone proceeds.

Also: CountDownLatch is one-shot. Once it hits 0, it's done. CyclicBarrier resets.

No Clojure wrapper - and that's fine

Barriers and latches are niche enough that a Clojure wrapper would add nothing. Java's API is already clean. Import and use directly.

Refs & STM

Coordinated, synchronous state. Multiple refs change together atomically. Like a database transaction, but for in-memory values.

Why not bank transfers?

You're right - real bank transfers happen against a database with ACID transactions. The "bank account" example is academically correct but practically useless. STM is for in-process, in-memory coordination.

Real example: game state
;; An entity's position and the world's grid
;; must stay consistent with each other
(def player-pos (ref {:x 5 :y 3}))
(def world-grid (ref (make-grid)))

(defn move-player! [dx dy]
  (dosync  ; transaction: both change or neither
    (let [old-pos @player-pos
          new-pos {:x (+ (:x old-pos) dx)
                   :y (+ (:y old-pos) dy)}]
      (when (walkable? @world-grid new-pos)
        (alter world-grid remove-entity old-pos)
        (alter world-grid place-entity new-pos)
        (ref-set player-pos new-pos)))))

If another thread modifies world-grid during this transaction, STM detects the conflict and retries automatically. The player never ends up in an invalid state - never on an unwalkable tile, never at one position while the grid shows them at another.

When do you need coordination?

Anytime you have two or more values with an invariant between them:

  • Game state: entity position + world grid must agree
  • Resource pools: available count + assigned set must sum to total
  • Cache + index: if a value is in the cache, its key must be in the index (and vice versa)
  • Order book: bids list + asks list + matched trades must stay consistent

If you could use separate atoms for each, you'd get a window where one is updated and the other isn't. Other threads reading during that window see inconsistent state.

Why doesn't Java have this?

STM requires immutable data to work. When a transaction retries, it needs the old value to still be intact. Java's mutable objects can't provide this guarantee - if you put a HashMap in a ref and someone mutates it from outside the transaction, everything breaks.

Clojure's persistent data structures make STM possible. The old value is always available for free (structural sharing). This is why immutability is foundational to Clojure's whole concurrency model.

Honest take

Refs are rarely used in production Clojure. Most apps have single independent values (atoms) or use a database for coordination. But when you genuinely need in-memory multi-value consistency - an order matching engine, a simulation, a game - refs are elegant.

takeaway

The Pragmatic Middle Ground

Immutability is the real hero.

Most concurrency bugs vanish when data can't be mutated. Clojure's persistent data structures mean you almost never need synchronization for reads.

Managed references for the rest.

When you do need mutable state, atoms (95%), refs (4%), and agents (1%) handle it with clear semantics. No manual lock ordering, no forgotten unlocks.

The JVM is always there.

CyclicBarrier? CountDownLatch? Phaser? Semaphore? StampedLock? All one import away. Clojure wraps the common cases and lets you interop for the rest.

"I also considered languages (like Haskell) with more rigorous control over side effects, but decided that Clojure's less-dogmatic approach was preferable."

Less dogmatic doesn't mean less safe. It means safety by default (immutability) with escape hatches when you need them (managed references, j.u.c. interop). No type-system tax. No monad tutorials required.

appendix a

Semaphore

A counter that limits how many threads can access a resource concurrently. Like a lock, but for N threads instead of 1.

Semaphore(3) - allow 3 concurrent connections permits = 3 Thread A: acquire() -> permits = 2, proceed Thread B: acquire() -> permits = 1, proceed Thread C: acquire() -> permits = 0, proceed Thread D: acquire() -> permits = 0, BLOCKED Thread A: release() -> permits = 1 Thread D: unblocked! -> permits = 0, proceed
Real example: database connection limiter
(import '[java.util.concurrent Semaphore])

;; Only allow 10 concurrent DB queries
;; (our connection pool has 10 connections)
(def db-permits (Semaphore. 10))

(defn query-db [sql]
  (.acquire db-permits)
  (try
    (jdbc/execute! ds [sql])
    (finally
      (.release db-permits))))

;; 100 threads can call query-db, but only 10
;; will actually hit the DB at once. The rest
;; queue up politely instead of overwhelming
;; the connection pool.

When to use

  • Connection limiting - cap concurrent DB/API/file connections
  • Rate limiting - only N concurrent requests to an external API
  • Resource pools - manage access to a fixed set of expensive resources
  • Throttling - prevent overwhelming a downstream service

Semaphore(1) = Lock

A semaphore with 1 permit behaves like a mutex/lock. But unlike ReentrantLock, it's not reentrant and not thread-owned - any thread can release it, not just the one that acquired it. This makes it useful for asymmetric producer-consumer patterns.

Java API

Semaphore s = new Semaphore(10);
s.acquire();         // block until permit
s.tryAcquire();      // non-blocking, returns bool
s.tryAcquire(5, SECONDS); // with timeout
s.release();          // return permit
s.availablePermits(); // how many left?

appendix b

Phaser

A flexible barrier where threads can register and deregister dynamically. Like CyclicBarrier, but threads can join and leave mid-computation.

Phaser vs CyclicBarrier CyclicBarrier(3): always exactly 3 threads Thread count is fixed at creation. If one thread dies, the other 2 wait forever. Phaser: threads come and go Phase 0: A, B, C registered (3 parties) Phase 1: D joins (register()), now 4 parties Phase 2: B leaves (arriveAndDeregister()), now 3 Phase 3: only A, C, D need to sync
Real example: dynamic web scraper
(import '[java.util.concurrent Phaser])

;; Scrape pages in waves. Each wave discovers
;; new links -> new workers join the next wave.
(def phaser (Phaser. 1)) ; main thread is party 0

(defn scrape-page! [url]
  (.register phaser)  ; join the party
  (future
    (let [links (extract-links (http/get url))]
      (doseq [link links]
        (scrape-page! link))  ; spawn more
      (.arriveAndDeregister phaser))))

(scrape-page! "https://example.com")

;; Wait for current wave to complete
(.arriveAndAwaitAdvance phaser)

When to use

  • Dynamic work pools - workers can join and leave between phases
  • Iterative algorithms - where the number of participants changes per iteration
  • Multi-wave processing - phase 1 discovers work, phase 2 processes it
  • Test harnesses - coordinate variable numbers of test actors

Phaser replaces both

Phaser can act as a CyclicBarrier (fixed parties, reusable) or a CountDownLatch (arrive without waiting). It's the most general synchronizer in j.u.c. but also the most complex. Use the simpler tools when they suffice.

Phase number

Every time all parties arrive, the phase number increments. You can query it with .getPhase() to know which iteration you're on. Useful for termination conditions: "stop after phase 10" or "stop when no new work was discovered."

appendix c

java.util.concurrent Without Clojure Wrappers

All of these are used via direct Java interop in Clojure. No wrappers needed - the Java APIs are clean enough.

Class What It Does Real Use Case Clojure Usage
CountDownLatch N threads count down, waiters unblock at 0 Wait for all services to initialize before accepting traffic (.await latch)
CyclicBarrier N threads sync up, then all proceed. Reusable. Parallel simulation steps (cellular automata, physics ticks) (.await barrier)
Phaser Dynamic barrier - threads join/leave between phases Web crawler waves, dynamic worker pools (.arriveAndAwaitAdvance p)
Semaphore Limit concurrency to N threads Cap DB connections, rate limit API calls (.acquire s) / (.release s)
Exchanger Two threads swap objects at a meeting point Double buffering (one fills, one drains, swap) (.exchange ex obj)
StampedLock Optimistic reads + write lock. Fastest for read-heavy. In-memory caches with rare updates (.tryOptimisticRead sl)
ForkJoinPool Work-stealing pool for recursive divide-and-conquer Parallel sort, tree traversal (pmap uses this) Clojure's pmap / r/fold
ScheduledExecutorService Run tasks on a schedule or with delays Periodic cache refresh, delayed retries (.scheduleAtFixedRate ses ...)
CompletableFuture Rich async pipeline (thenApply, compose, allOf) Chaining async HTTP calls with error handling Usually use manifold instead

All available via (import '[java.util.concurrent ClassName]). These are battle-tested, heavily optimized, and well-documented. Don't reinvent them.
